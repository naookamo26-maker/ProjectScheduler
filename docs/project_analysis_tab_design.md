# プロジェクト分析タブ 設計案（相談メモ）

スケジューリング結果を要約する5番目のタブ「プロジェクト分析」の設計案。
**未実装**。着手の可否・範囲を決めるための検討メモとして残す。

数値はすべて、同梱の大規模サンプル
（`data/Project_Schedule_Sample_AAA_Large.pschedule`、1,916ジョブ / 16,230タスク /
15チーム / 10ワークフロー / 6マイルストーン）を実際にスケジューリングして得た**実測値**。

---

## 1. 前提

1. **このツールは工数管理をしない。** スケジューリングの基礎になっている日数は
   「タスクを実行する期間」であって、実際の工数を表していない。したがって
   **人日・工数という語も指標も使わない。**
2. **状態（未着手・進行中・完了）は件数で数える。** 所要日数による重み付け・按分はしない。
3. **チームのライン数上限は既定で「指定なし」。** 計画段階で割当人数が確定していることは
   少なく、「このスケジュールを達成するには何本必要か」をシミュレーションしてから
   検討するサイクルを回す。上限を明示するのは、開発冒頭に人を入れられない・
   早めに引き上げる・一定期間だけ絞る、といった例外の表現に使う。
4. **このタブは結果を纏めるだけ。** 再計算もパラメータ操作も持たない。
   配置の調整はガントチャートタブの役目であり、このタブはその結果を受け取るだけにする。

4つ目の帰結として、**「上限を外して再計算する」機構を一切持たない**。
必要ライン数の推定、締切超過の原因分類（増員で解消するか否か）、配置比率スキャンは
いずれも反実仮想の再計算を伴うため、採らない。

外しても成立するのは、前提3のおかげである——**上限を置かなければ、スケジューリング結果の
同時タスク数がそのまま「必要な本数」になる。** 反実仮想を計算しなくても、
結果を素直に数えるだけで「何本要るか」が読める。

> **承知のうえで失う情報**: 締切超過が「人を足せば消えるのか、依存の鎖が長すぎて
> 消えないのか」は、このタブからは分からなくなる。検証時の実測では、サンプルの
> 413件はすべて前者だった（上限を外すと0件になった）。ただし
> **上限を1つも設定していないプロジェクトでは、超過はすべて依存由来だと定義上わかる**
> ため、「指定なし」を既定にする限り実害は小さい。将来必要になったら、このタブではなく
> **ガントチャートタブ側の機能**（比較実行）として足すのが筋がよい。

## 2. 画面構成

既存4タブの流儀（縦積み・`QGroupBox`・`CollapsibleSection`・表示専用）を踏襲する。

```
[ツールバー] ガントチャートタブの計算結果を集計している旨の表示   [表をコピー] [CSV]
[KPIタイル ×6]
[QGroupBox] マイルストーン別サマリー   … 内訳の切り替え（全体／チーム別／ワークフロー別）
[QGroupBox] チーム別サマリー           … 同時タスク数の推移（積み上げ）+ 表 + 選択チームの詳細
[QGroupBox] ワークフロー別サマリー     … 粒度の切り替え（月次／週次／日次）+ 表
[QGroupBox] 要注意タスク（締切超過 上位）
```

**基準日ピッカーと配置比率の選択は置かない。** 状態の集計は「今日」で固定する
（実績を持たせた後は、記録された状態を数えるだけになり基準日の概念自体が消える）。

### 2-1. ヘッドライン（KPIタイル）

6枚。全体感を最初に受け取る場所なので、すべて全体の値にする。

規模（ジョブ件数 / タスク件数）／ 計画期間 ／ **タスクの状態（完了・進行中・未着手の件数）**／
**同時タスク数のピーク**（実測 259本 / 2027-03）／ 締切に間に合わないタスク ／ 開始固定日の違反。

### 2-2. マイルストーン別サマリー — 内訳を切り替える

**1行1マイルストーンという構造は変えず、右側の「内訳」の列群だけを差し替える。**

- **全体**: ジョブ件数 / タスク件数 / 完了・進行中・未着手
- **チーム別**: チームごとのタスク件数（15列）
- **ワークフロー別**: ワークフローごとのタスク件数（10列）

基本列（マイルストーン / 締切日 / 残日数 / 最終終了日 / スラック / 超過件数 / 判定）は
3モードとも共通で残す。行を展開する方式（マイルストーン×チームの行を出す）も検討したが、
**「そのマイルストーンが間に合うか」の情報が内訳のたびに繰り返されて読みにくくなる**ため、
基本列を固定する形にした。

内訳の列は多くなるので横スクロールする。件数の大小は淡い背景の濃さでも示す。

**主役はスラック列**（締切 − そのマイルストーンに属するタスクの最終終了日）。実測値:

| マイルストーン | 締切 | タスク件数 | 最終終了日 | スラック |
| --- | --- | ---: | --- | ---: |
| ヴァーティカルスライス | 2026-06-30 | 1,478 | 2026-10-21 | **−113日** |
| ファーストプレイアブル | 2026-12-18 | 3,334 | 2027-02-13 | **−57日** |
| アルファ | 2027-06-30 | 4,445 | 2027-07-23 | **−23日** |
| ベータ | 2027-12-17 | 4,195 | 2027-11-16 | +31日 |
| コンテンツロック | 2028-03-31 | 2,348 | 2028-02-25 | +35日 |
| マスターアップ | 2028-06-30 | 430 | 2028-04-27 | +64日 |

符号がきれいに分かれ、計画が前半に寄りすぎていることが1列で読める。

> **集計上の注意**: タスクは `job_task_overrides.milestone_id` でジョブ既定と別の
> マイルストーンに付け替えられるため、**1ジョブが複数マイルストーンにまたがりうる**。
> ジョブ件数列は単純合計すると総ジョブ件数と一致しない。合計行では「延べ」と明記し、
> 実数はKPIタイル側を正とする。タスク件数はタスク単位なので重複しない
> （チーム別・ワークフロー別の内訳も、行方向の合計はタスク件数と必ず一致する）。

### 2-3. チーム別サマリー

スパークラインの一覧は**画面占有率が高すぎるため置かない**。
**全体を1枚、個別を1枚**の構成にする。

1. **同時タスク数の推移（チーム別・積み上げ）** — 全体感を出す主役の図。
   いつ全体が混むかと、その内訳がどのチームかが1枚で読める。
2. **選択したチームの同時タスク数と上限** — 表の行選択に連動する。塗り＝同時タスク数、
   破線＝設定上限。**上限が「指定なし」のチームでは破線を描かない**ので、
   線が無いこと自体が「まだ人数を決めていない」ことの表示になる。

表の列: チーム / 上限設定 / ピーク / ピーク時期 / 上限に張り付いた日数 / タスク件数 /
押し出された件数 / 超過件数。

> **実装時の決定（原案から変更）**: 「上限設定」列は実装時に削った。ライン数
> 上限は`team_capacity_changes`で期間中に変動しうるが、この列でどう単一の値
> として表示するかが原案では未定義だった（開発開始日時点の値を出す／変動幅を
> 出す等の案があったが、いずれも「上限に張り付いた日数」列と情報が重複・
> 混同しやすい）。実装時の表の列は
> チーム / ピーク / ピーク時期 / 上限に張り付いた日数 / タスク件数 /
> 押し出された件数 / 超過件数の7列（`docs/screens.md`のタブ5節参照）。

**読みどころ**: サンプルでは「上限設定」と「ピーク」が15チームすべて同じ値になる。
上限を設定すると、スケジューラは超えない代わりに後ろへ押し出すので、
**どのチームも一度は上限に張り付く**——これが締切超過413件の正体にあたる。
上限を「指定なし」にすれば、この列は素直に「必要な本数」を指すようになる。

「押し出された件数」は `Resource_Adjusted`。**上限を設定したチームでしか発生しない**ので、
「指定なし」が既定の運用ではほとんどの行が0になり、**0でない行が
「制約が効いている場所」を指す**。実測では全体の10.4%（1,686件）が押し出されていた。

### 2-4. ワークフロー別サマリー — 粒度を切り替える

期間ごとの**稼働タスク件数**（その期間に1日でも走っているタスクの件数）の積み上げ面グラフに、
**月次 / 週次 / 日次**の切り替えを付ける。開始件数ではなく稼働件数にするのは、
長いタスクが期間をまたぐときに山が消えるため。

**日次で全期間（実測587稼働日）を一度に描くと横に潰れて読めない。**
ガントチャートタブと同じ**ホイールでズーム・中ボタンでパン**の操作系を付け、
日次に切り替えたときは既定の表示範囲を絞る（数か月ぶん）。
週次（実測117週）までは全期間を一度に出して問題ない。

表: ワークフロー / ジョブ件数 / タスク件数 / ジョブ所要期間の中央値 / 超過件数。
所要期間は「1ジョブの最初のタスク開始〜最後のタスク終了」の暦日で、**足し合わせずに
中央値だけを見る**——パイプラインの長さの比較に使う量であって、量の集計ではない。

### 2-5. 要注意タスク

超過日数の降順で上位20件。列: ジョブ / タスク / チーム / マイルストーン / 計画終了日 /
超過日数 / 押し出し。ダブルクリックでジョブ作成タブへ飛び、修正の入口にする。

## 3. 集計の定義

| 用語 | 定義 |
| --- | --- |
| 件数 | タスクの本数。**所要日数で重み付けしない。**このタブの唯一の「量」の単位 |
| 同時タスク数 | ある日にそのチームで走っているタスクの本数。**上限が「指定なし」のチームでは、これがそのまま「必要な本数」になる** |
| ピーク | 同時タスク数の最大値（稼働日のみ）。全体のピークは各チームのピークの和にはならない（時期がずれるため） |
| 上限に張り付いた日数 | 同時タスク数＝設定上限となった稼働日の数。**「設定した上限が実際に効いたか」**を表す。上限が「指定なし」のチームでは空欄 |
| 押し出された件数 | `Resource_Adjusted` が立ったタスクの件数。上限を設定したチームでしか発生しない |
| スラック | マイルストーンの締切 − そのマイルストーンに属するタスクの最終終了日（暦日） |
| 状態 | 未着手 / 進行中 / 完了 の3区分、**件数**。実装時の決定（当初案の日付推測から変更）: `job_task_overrides.status` にユーザーが手動で記録した実データを集計する。基準日という概念は使わない。日付・実績を持つ前の状態表示という論点（後述の確認事項5）はこの決定で解消済み |
| 所要期間 | 1ジョブの最初のタスク開始〜最後のタスク終了（暦日）。**合計は取らず中央値だけを見る** |
| 帰属 | チーム・マイルストーンとも、上書きを解決したあとの**実効値**（`result_df` の `Team_ID` / `Milestone_ID`） |

**意図的に持たない指標**: 工数・人日（所要日数の総和）、稼働率、加重した進捗率、
必要ライン数（上限を外した反実仮想）。前2つは「日数＝期間であって工数ではない」という
前提に反し、3つ目は状態を件数で数える方針に反し、4つ目は再計算を伴うため。

なお**「上限に張り付いた日数」は残す**。上限を設定したチームに限れば、これは
反実仮想を含まない結果の素直な読み取りで、「設定した上限が実際に効いたか」を
答える唯一の列になるため（稼働率のように分母を必要としない）。

## 4. 周辺への影響

### 4-1. リソースヒストグラムの廃止（基本情報設定タブ）

廃止する。影響範囲:

- `gui/resource_histogram.py` のうち**描画部分（`build_histogram_scene`・
  `ResourceHistogramView`）は削除**。ただし**純粋関数 `compute_step_segments` は残す**
  ——プロジェクト分析タブの「設定上限の階段線」にそのまま使うため
  （同関数のdocstringが元々この汎用性を意図して書かれている）。
- `gui/tab_basic_info.py`: 「チーム」枠は現在**左＝チームツリー / 右＝ヒストグラムの
  3:7分割**。ヒストグラムを外すと `QSplitter` ごと不要になり、**チームツリーが全幅**になる
  （ライン数の変動点を一覧しやすくなるので、この点はむしろ改善）。
- `tests/test_resource_histogram.py`: 純粋関数のテストは残し、描画のテストは削除。
- `docs/screens.md` のタブ1「リソースヒストグラム」節を削除し、「チーム」枠の構成を書き直す。

上限の推移そのものを見たくなった場合は、プロジェクト分析タブの**チーム別の詳細グラフ
（同時タスク数＋上限の破線）が上位互換**になる——上限だけでなく、それに対して実際
どれだけ詰まっているかが同時に見えるため。

### 4-2. ライン数上限の3状態化（スキーマ v15）

0とNULLを区別する。

- **NULL＝指定なし**（上限を設けない。**新規チームの既定**）
- **0＝稼働なし**（その期間はチームが動かない。既存の意味を維持）
- **N＝N本**

`teams.max_lines` と `team_capacity_changes.lines` の `NOT NULL` を外す。
SQLiteは `ALTER TABLE` で制約を直接変更できないので、**テーブルを作り直して移し替える**
（v11で同じ CHECK 緩和を同じ手順でやっている前例がある）。

移行では**既存の値をNULLに書き換えない**——「意図して設定した本数」と
「既定値1のまま放置された本数」を区別する情報が無いため。既存ファイルは
全チーム上限ありのまま開く。

UIでは0とNULLを見分けられる必要がある。`widgets_common.py` の `DefaultAwareSpinBox` /
`OptionalDateEdit` が「特別な値を持つ入力欄」の前例になる（スピンボックスの最小値の
1つ下を「指定なし」の表示にする `specialValueText` が素直）。

現在「＋チーム」は**ライン数1**でチームを追加する（`docs/screens.md`）。1本は極めて
厳しい制約で、初めて使う人は全タスクが直列に伸びる理由が分からない。
既定を「指定なし」にするとこの落とし穴も同時に消える。

`CLAUDE.md` の規約により、スキーマ変更は**全テスト（210件）実行の対象**。

### 4-3. `Resource_Adjusted` の位置づけ

上限が既定で無くなると押し出しが起きないので `Resource_Adjusted` は**既定構成では
常にFalse**になる（実測 1,686件 → 0件）。`ResourceOverflowError` も発生しなくなる。

廃止せず、**「上限を設定しているチームがある場合にだけ意味を持つ表示」**として
位置づけ直す。プロジェクト分析タブでは、チーム別の表に「押し出された件数」列として置き、
0でない行が制約の効いている場所を指す形にする。ガントチャートタブ側の橙色表示も同じ扱い。

## 5. 実装方針

- **スケジューリング結果はガントチャートタブと共有する。** このタブは自分では計算を
  起こさず、結果だけを受け取る。現在 `GanttTab` が `_result_df` と `_computed_revision` を
  自前で抱えているので、キャッシュ判定・ワーカー管理・結果の配布を `ScheduleCache`（仮）
  として `MainWindow` に集約する。既存の**「要求時点のrevisionを刻む」「実行中の
  ワーカーを全件追跡して終了を待つ」**という2つの決定はそのまま移す
  ——どちらも実際の不具合から入った規約なので、作り直すと踏み直す。
- **結果が無いときの表示。** このタブを先に開いた場合や未完成なプロジェクトの場合は、
  **ダイアログを出さず**タブ内に理由を出す（ガントチャートタブと同じ方針）。
  ガントチャートタブを一度も開いていない状態でも計算が走るよう、`ScheduleCache` は
  どちらのタブからでも起動できるようにする。
- **集計はQt非依存の純粋関数に分ける**（`gui/summary_metrics.py`）。
  `pytest -m scheduler`（PySide6不要）の階層でテストできる。
- **同時タスク数は差分＋累積和**で `O(タスク数 + 日数)`。16,230タスクの全集計が
  **実測0.1秒未満**なので、粒度の切り替えも再集計ではなく**日次の配列を1本持って
  畳み込む**だけでよい。バックグラウンド化は不要。
- **`result_df` の変更は不要。** 件数と同時タスク数しか使わないので
  `Start_Date` / `End_Date` で足り、`project_scheduler.py` に手を入れずに済む。
- **描画は `QGraphicsScene` 直接描画を踏襲。** 積み上げ面・折れ線・階段線はこれで足りる。
  日次のズーム／パンは `gui/gantt_view.py` の `GanttGraphicsView` を再利用できる
  （リソースヒストグラムが同じやり方で再利用していた前例がある）。
  QtWebEngine（Plotlyを画面内に埋める案）は `.exe` が桁で膨らむので採らない。
- **表示専用タブ。** `@undoable` の対象は増えないが、規約どおり `capture_ui_state()` /
  `restore_ui_state(state)` は実装する（内訳モード・粒度・選択行・セクション開閉・
  スクロール位置）。DBには保存しない。

## 6. 作る順番

| 順 | 内容 | 理由 |
| --- | --- | --- |
| 1 | ライン数上限の3状態化（スキーマv15）＋ 基本情報設定タブのUI ＋ 新規チームの既定を「指定なし」に ＋ リソースヒストグラムの廃止 | 分析タブの中身がこの意味論の上に乗る。ヒストグラムの廃止も同じタブを触るので**まとめて1回で済ませる** |
| 2 | `summary_metrics.py` ＋ タブの器 ＋ KPIタイル ＋ マイルストーン別の表（内訳切り替えを含む） | グラフを1枚も描かずに価値の大半が出る |
| 3 | `ScheduleCache` の抽出 ＋ チーム別サマリー（積み上げ＋詳細） | 二重計算の解消と、全体感の主役の図 |（実装済み。`gui/schedule_cache.py`・`gui/team_summary_view.py`）
| 4 | ワークフロー別サマリー（粒度切り替え・日次のズーム）＋ 要注意タスク一覧 ＋ タブ間連携 | 日次のズーム／パンだけ実装量があるので最後に回す |

段階2の時点では `GanttTab` から結果を受け取るだけで動かせるので、`ScheduleCache` の
抽出は段階3まで遅らせられる——表とタイルが妥当だと確認できてから作り替えに入れる。

段階3のチーム別サマリーの表からは、実装時のフィードバックで「上限設定」列
（§2-3原案）を削った——上限が期間中に変動するチームの表示方法が未定義だった
ため、列自体を無くして解消した。詳細は`docs/screens.md`のタブ5節を参照。

## 7. 確認したい点

1. **（解消済み）上限に張り付いた日数を残してよいか** — 第2版では削ったが戻したい
   （§3の末尾）。残す方針で実装済み（`gui/summary_metrics.compute_team_summary_rows`）。
2. **マイルストーン別の内訳の出し方** — 基本列を固定し、右側の内訳列群だけを差し替える案。
3. **日次の表示範囲** — 全期間587稼働日を一度に描くと潰れるので、ガントチャートタブと
   同じズーム／パンを付け、既定では数か月ぶんに絞る案。
4. **状態の粒度** — タスク単位に持ち、ジョブの進捗は「完了タスク件数 ÷ 総タスク件数」の
   派生とする案（ジョブに独自の状態を持たせない）。二重管理を避けるため。
5. **（解消済み）実績を持つ前の状態表示** — 当初案は「今日の時点で計画上どの状態か」を
   日付から推測する方式だったが、`job_task_overrides.status`
   （タブ3「タスク上書き」の「状態」列）にユーザーが実際に記録した値を使う方式に変更した。
   §3の「状態」の定義を参照。
6. **（解消済み）チームが13以上のときの色** — 既存パレットは12色で13番目以降は無彩色に
   潰れる（サンプルは15チームなので実際に3チームが灰色になる）。積み上げグラフでは
   目立つので、**凡例とツールチップの文字で必ず補う**前提にしたい。この提案どおり実装
   済み——凡例は別途置かず、各系列で最も横幅が広い区間の中央にチーム名を直接
   ラベル表示し、ツールチップでも補う（`gui/team_summary_view.py`）。
