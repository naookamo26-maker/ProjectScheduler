# 利用者向けドキュメント アウトライン

利用者向けドキュメント（ユーザーガイド）の内容・方針を、執筆前に固めたもの。
本文はこのアウトラインに従って書く。方針を変えるときは、先にここを更新する。

## 形式と作り方

- **配布形式はPDF**。原稿はPDFで直接書かず、次の3層で管理する。
  - 原稿: `docs/user_guide/*.md`（Markdown。差分が見えるようにする）
  - 画像: スクリプトで自動撮影したPNG（撮影用サンプルを開き、offscreenで各画面を撮る）。
    画面が変わったらコマンド1つで撮り直せるようにする
  - 出力: ビルドスクリプトで原稿＋画像からPDFを生成する
- **読者**は計画を作る人（PM・進行管理）。計画を見るだけの人向けの分冊は作らない。
- **言語**はまず日本語のみ。翻訳は後で行う（撮影スクリプトは表示言語を切り替えて撮れるようにしておく）。
- 用語は `docs/i18n_glossary.md` の日本語に揃える。

## 執筆方針

1. **期間の計画であって、工数の計画ではない。** 0章で目立つ囲みにして強調し、
   日数・ライン数・分析の指標が出てくる箇所（下の目次の★）でも毎回、同じ見た目の
   小さな囲みで念押しする。ここを誤解されると、ツールの意味が薄れる。
   囲みの目印は、日数（期間）の話なら「期間≠工数」、ライン数の話なら「ライン数≠人数」にする
   （ライン数の説明に「期間≠工数」と付くのは不自然なため）。
2. **利用者の視点で書く。** 内部処理・設計上の都合・性能には触れない。
3. **使い方の幅を狭めない。** 「〜はできません」「〜専用です」と制限を並べず、
   自由度として書く（例: チームは部署でも個人でも協力会社でもよい。
   複数の業務を1つの計画にまとめてもよい）。
4. **題材はゲーム開発で統一する。** 汎用的な題材では身近に感じられず分かりづらかったため、
   例・サンプル・活用例はゲーム開発にそろえる。ただし使い道を狭めないよう、題材はあくまで
   例であり、規模も用途も限定しないこと（0章）は残す。
5. **HTMLガントチャート出力は特色として扱わない。** ガントチャートの節で操作だけ短く書く。
6. **サンプルファイルの配布には触れない。** 画面の例はサンプルを使うが、「付属のサンプルを開く」
   のような記載はしない（配るかどうかは未定のため）。
7. **画面写真の番号の目印は、上から下へ順に振る。** 同じ高さのものは左から右へ。表の説明も同じ順に並べる。
8. **未実装の機能は載せない**（プロジェクト分析タブの要注意タスク一覧・タブ間連携など）。

## 目次と各章の要点

★ = 「期間≠工数」の念押しを入れる箇所

### 0. このツールの狙い・目的

- **一言で**: チームが同時にこなせる作業量と締切を踏まえて、無理なく進められる
  期間の計画を組み立て、関係者と合意しながら進めるためのツール。
- **★大切な前提: これは「期間」の計画です**（章の中で最も目立たせる囲み）
  - 各タスクの「日数」は、着手から完了までにかかる**期間**。費やす人手（工数・人日）ではない。
  - 例: 「10日のタスク」は「10日後に仕上がる」という意味で、「10人日の作業量」ではない。
  - チームの「ライン数」は、同時に並行して進められる作業の**本数**。人数そのものではない。
  - 工数は集計・管理しない。コストや人員の見積もりは別の手段と組み合わせる。
- **どんな困りごとを解決するか**（困りごと → このツールでは）
  - 表計算ソフトの計画表で入力ミス・参照ミスが起きる → 名前を選び、線でつなぐだけで組み立てられる
  - 作業のつながりの全体像が見えない → 作業の流れを図で見ながら作れる
  - つながりは正しくても、チームの手が回らない日程になる → 同時に進められる本数と休日を踏まえて日程を自動で組む
  - 作業がぶつかったとき、どれを先にするかで揉める → 優先度に従って一貫したルールで決まる
  - 締切に間に合うかどうかが見えない → 間に合わない作業と遅れの日数が一目で分かる
  - 同じ流れの仕事を何件も手で並べるのは大変 → 作業の流れを型として作り、必要な数だけ展開できる
  - 合意した計画がいつの間にか変わっている → 合意した計画を「確定」として残せる。変更は試してから明示的に確定する
- **使い方の流れ**（サイクル図）: 計画を作ってシミュレーション → 合意（確定）→
  進み具合の反映 → 振り返って必要なら再計画 → 再合意、の繰り返し。
- **規模も用途も限定しません**: 数件の作業からなる小さな計画から、数千件の作業を
  抱える大きなプロジェクトまで。チームの割り当て方も自由。→ 8章の活用例へ誘導する。

### 1. はじめに

- 基本用語: プロジェクト／マイルストーン／チーム★（ライン数）／ワークフロー／
  タスク★（日数）／ジョブ／依存
- 用語どうしの関係を1枚の図で示す（ワークフロー＝作業の流れの型、ジョブ＝型から作った実際の仕事、など）

### 2. 起動と初期設定

- 起動のしかた
- プロジェクトファイルの扱い（新規作成・開く・保存、未保存の `*` 表示、元に戻す／やり直す）
- オプション設定（表示言語など）

### 3. クイックスタート

- 小さな計画を一から作る（題材は8章Bの「アップデートの制作」をごく小さくしたもの。章をまたいで話をつなげる）

### 4. 画面の見方

- メニュー
- 計画の状態帯
- （ファイルの新規作成・開く・保存と `*` 表示、Undo は、3章のチュートリアルで必要になるため2章で説明した）

### 5. タブごとの操作

- 基本情報設定 ★（ライン数）: プロジェクト概要、マイルストーン、チーム、休業日
- ワークフロー設計 ★（タスクの日数）: ノードビュー／テーブルビュー、依存、依存テンプレート
- ジョブ作成 ★（日数上書き）: ジョブ一覧、絞り込み、タスク上書き（状態・開始固定日を含む）、依存先ジョブ
- ガントチャート: 絞り込み、タスクの編集、配置コントロール、HTMLガントチャートの出力（操作だけ短く）
- プロジェクト分析 ★（指標は件数や本数で表しており、工数ではない）

### 6. 計画の確定と再計画

- 確定する
- 変更案を試す、変更を確定する／破棄する
- 全面再計画

### 7. 日程の決まり方

利用者が操作・判断に使うルールだけを書く（内部処理の説明はしない）。

- 依存（先行タスクが終わってから始まる）
- ライン数（同時に進められる本数を超えない）
- 優先度（ぶつかったときは優先度の高いジョブが先）
- 休業日・祝日
- 開始固定日
- 配置コントロール（「最速」〜「ギリギリ」）
- 締切に間に合わないときの表示

### 8. 活用例

- **A. 新作タイトルの制作**（大きな計画を粗い粒度で）: 1タスクを数週間〜数か月の
  まとまりにし、締切に間に合いそうか、どの時期にどのチームが混み合うか、
  同時に何本の作業を走らせる必要があるかを見る。確定後はマイルストーンごとに
  振り返って再計画する。★粗くしても日数は「期間」であることを念押しする。
- **B. アップデートの制作**（小さな計画を細かい粒度で）: 1タスクを数日単位にし、
  定例ミーティングで「状態」を更新する。実際の開始日が予定とずれたら開始固定日で
  合わせ、再計画で後ろへの影響を見る。言い回しは「進捗を管理する」ではなく
  「進み具合を反映して見通しを更新する」とする。
- 「段階的に細かくする」使い方は載せない（現状の操作では複雑なため。
  ツール側の支援は `docs/roadmap.md` §12 で検討する）。

### 9. 困ったとき

- 循環依存のエラーが出た
- 締切に間に合わないタスクが出た
- 日程が思ったように並ばない
