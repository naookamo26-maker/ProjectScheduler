# 活用例

このツールは、計画の規模や、タスクをどこまで細かく分けるか（**粒度**）を問いません。
この章では、ゲーム開発を題材に、使い方の異なる2つの例を紹介します。

| | A. 新作タイトルの制作 | B. アップデートの制作 |
| --- | --- | --- |
| 規模 | 大きい（1年以上、多くのチーム） | 小さい（数週間、少人数） |
| 粒度 | 粗い（1タスク＝数週間〜数か月） | 細かい（1タスク＝数日） |
| 主な目的 | 全体の見通しを立て、関係者と合意する | 進み具合を反映しながら、見通しを更新する |

## A. 新作タイトルの制作（大きな計画を粗い粒度で）

発売までの1年以上にわたる制作を、キャラクター・背景・カットシーンといった制作物ごとに計画します。
細かい作業まで並べるのではなく、**工程のまとまり**をタスクにして、全体の見通しを立てることに使います。

### 1. 作業の流れを型にする

「キャラクター制作」「背景制作」「カットシーン制作」のように、制作物の種類ごとにワークフローを作ります。
タスクは「モデル制作」「モーション制作」のような工程の単位にし、日数は数週間〜数か月の粒度で見積もります。

!!! kikan-note "粗く分けても、日数は「期間」です"
    「モデル制作 30日」は、そのキャラクターのモデルが**着手から30営業日で仕上がる**という意味です。
    粒度を粗くしても、作業量（工数）を見積もっているわけではありません。

### 2. 制作物をジョブとして並べる

主人公・ヒロイン・魔王…、始まりの村・王都…のように、制作物ごとにジョブを作り、
それぞれをどのマイルストーン（アルファ版・ベータ版など）までに仕上げるかと、優先度を決めます。
似た制作物は「複製」を使うと早く作れます。
カットシーンが登場キャラクターのモデルを待つ、といった制作物どうしの待ち合わせは、依存テンプレートと依存先ジョブで設定します。

### 3. どのチームが、いつ、どれだけ混み合うかを見る

プロジェクト分析タブの「チーム」で、各チームが同時に抱える作業の本数を週ごとに確かめます。

<figure>
<img src="images/analysis_team.png" alt="チームごとの同時タスク数">
<figcaption>チームごとの同時タスク数の推移</figcaption>
</figure>

計画の初めは、チームのライン数を「**指定なし**」にしておくのがおすすめです。
すると、グラフのピークから「この計画どおりに進めるには、各チームが同時に何本の作業を進められる必要があるか」が読み取れます。
そのうえで、実際にはそこまで並行できないチームにだけ、ライン数の上限を設定します。

!!! lines-note "ピークの本数は人数ではありません"
    ピークが「4本」でも、4人必要という意味ではありません。
    同時に4つの作業を並行して進められる体制が要る、という意味です。
    実際に何人でどう分担するかは、チームの実情に合わせて判断してください。

### 4. 締切に間に合わない作業を見直す

ライン数の上限を入れると、締切に間に合わない作業が出てくることがあります。
ガントチャートで赤い太枠のタスクを探し、優先度・ライン数・日数・締切のどれを見直すかを検討します
（見直し方は「日程の決まり方」の章）。

<figure>
<img src="images/gantt_tab.png" alt="新作タイトルのガントチャート">
<figcaption>新作タイトルのガントチャート。体験版のためにアルファ版へ前倒しした「魔王城」が間に合っていません</figcaption>
</figure>

例えば、この計画では「魔王城」をアルファ版に間に合わせようとして間に合っていません。
「魔王城」の優先度を上げるか、背景モデルチームのライン数を増やせるか、体験版に入れる範囲を見直すか、といった選択肢を、関係者と一緒に比べられます。
条件を変えるたびに日程がすぐに組み直されるので、その場で試しながら話し合えます。

### 5. 合意したら確定し、節目ごとに見直す

関係者と合意できたら、計画を確定します。
その後は、アルファ版・ベータ版といったマイルストーンの節目や、月に一度などの区切りで計画を振り返ります。
変更が広い範囲に及ぶときは全面再計画で組み直し、改めて合意してから確定します
（「計画の確定と再計画」の章）。

## B. アップデートの制作（小さな計画を細かい粒度で）

配信中のゲームの冬のアップデートで、新キャラクター・新ステージなど数件の追加コンテンツを、数週間で制作する計画です。
タスクを数日単位に細かく分け、**実際の進み具合を反映しながら、配信までの見通しを更新する**ことに使います。

### 1. 数日単位で計画を立てて確定する

「仕様作成 3日 → アート制作 8日 → 実装 5日 → 調整 3日 → テスト 4日」のように、数日単位のタスクで作業の流れを作ります。
各コンテンツをジョブにし、配信日などの締切を決めて日程を組み立て、チームで合意したら確定します。

### 2. 定例のミーティングで状態を記録する

週に一度などの定例のミーティングで、各タスクの状態（未着手・進行中・完了）を記録します。
状態を記録しても、確定した日程はそのままです。

<figure>
<img src="images/update_plan_jobs.png" alt="状態を記録したジョブ作成タブ">
<figcaption>新キャラクターの状態。仕様作成とデータ作成が完了、アート制作が進行中です</figcaption>
</figure>

記録した状態は、プロジェクト分析タブの「タスクの状態」や、マイルストーンごとの完了・進行中・未着手の件数で確かめられます。

<figure>
<img src="images/update_plan_analysis.png" alt="状態の集計">
<figcaption>プロジェクト分析タブ。完了3件、進行中2件です</figcaption>
</figure>

### 3. ずれたら実際に合わせて、見通しを更新する

実際に作業を始めた日が予定とずれたタスクは、ガントチャートでバーを動かして、実際の開始日に合わせます。
日数の見込みが変わったタスクは、日数を変えます。
これらは変更案になるので、後ろのタスクや配信日への影響を確かめられます。

- 影響が小さければ、「変更を確定」して新しい見通しとして共有します。
- 配信日に間に合わなくなりそうなら、優先度や作業の範囲を見直して、変更案の段階で手を打ちます。

このように、確定した計画と実際の進み具合を並べて見ながら、配信までの見通しを定期的に更新していきます。
