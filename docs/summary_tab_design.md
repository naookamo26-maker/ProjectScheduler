# サマリータブ 設計案（相談メモ）

スケジューリング結果を分析・可視化するための5番目のタブ「サマリー」の設計案。
**未実装**。着手の可否・範囲を決めるための検討メモとして残す。

このメモの数値はすべて、同梱の大規模サンプル
（`data/Project_Schedule_Sample_AAA_Large.pschedule`、1,916ジョブ / 16,230タスク /
15チーム / 10ワークフロー / 6マイルストーン）を実際にスケジューリングし、
本メモの提案どおりに集計した**実測値**である。

---

## 1. なぜ作るか

この計画の**全体稼働率は50.8%**（期間平均、稼働日のみ）。チームは平均すると
半分しか埋まっていない。それでも最初の3マイルストーンは**113日・57日・23日**
遅れる。

矛盾ではない。負荷が**時間方向に偏っている**だけで、2026年4月〜2027年4月は
ほぼ全チームが80〜99%で飽和し、2027年7月以降は一気に空く。

**この事実は16,230本のバーを眺めても分からない。** ガントチャートタブは
「個々のタスクがいつ走るか」には答えるが、「計画全体が成立しているか」
「どこが詰まっているか」には答えない。サマリータブが引き受けるのはそこ。

## 2. このタブが答える3つの問い

個々の表・グラフを先に決めると、数字は並ぶが読み方の定まらない画面になる。
先に問いを3つに割り切り、そこへ表とグラフを割り当てる。

| 問い | 見たいもの | 答え方 |
| --- | --- | --- |
| この計画は成立しているか | 健全性 | 締切超過の件数・最大超過日数、マイルストーン別スラック、開始固定日の違反、リソース調整率 |
| どこにどれだけ仕事があるか | 構成 | マイルストーン別・チーム別・ワークフロー別の ジョブ数／タスク数／工数（人日） |
| いつ誰が忙しいか | 時系列 | チーム×月の稼働率ヒートマップ、チーム別ライン数推移、ワークフロー別タスク数推移、累積工数のS字カーブ |

3つ目を独立させたのは、**§1の食い違い（50.8%なのに113日遅れ）を説明できるのが
ここだけ**だから。落とすと「物量は分かるが、なぜ遅れるかは分からない」画面になる。

## 3. 画面構成

既存4タブの流儀（縦積み・`QGroupBox`・`CollapsibleSection`・表示専用）を踏襲する。

```
[ツールバー] 基準日 / 工数の単位 / 集計対象        [表をコピー] [CSVで書き出す]
[KPIタイル ×6]
[QGroupBox] マイルストーン別サマリー   … 表 + 累積工数S字カーブ
[QGroupBox] チーム別サマリー           … チーム×月 稼働率ヒートマップ + 表 + 選択チームのライン数推移
[QGroupBox] ワークフロー別サマリー     … 積み上げ面グラフ + 表
[QGroupBox] 要注意タスク（締切超過 上位）
```

### 3-1. ヘッドライン（KPIタイル）

「最初の3秒で受け取る結論」に絞り**6枚まで**。締切超過・固定違反は0件のときも
灰色のタイルとして残す（0であることの確認に価値があるため、異常時だけ現れる
作りにはしない）。

規模 / 期間 / 締切超過（赤）/ 開始固定日の違反（橙）/ リソース調整率 / 全体稼働率。

### 3-2. マイルストーン別サマリー

列: 締切日 / 残日数 / ジョブ数 / タスク数 / 工数 / 計画上の消化率 / 最終終了日 /
スラック / 超過件数 / 最大超過日数 / 判定。

**主役はスラック列**（締切 − そのマイルストーンに属するタスクの最終終了日）。
正負で色を分けた横棒を添える。実測値:

| マイルストーン | 締切 | タスク | 工数 | スラック |
| --- | --- | ---: | ---: | ---: |
| ヴァーティカルスライス | 2026-06-30 | 1,478 | 6,060 | **−113日** |
| ファーストプレイアブル | 2026-12-18 | 3,334 | 13,637 | **−57日** |
| アルファ | 2027-06-30 | 4,445 | 17,892 | **−23日** |
| ベータ | 2027-12-17 | 4,195 | 16,713 | +31日 |
| コンテンツロック | 2028-03-31 | 2,348 | 9,171 | +35日 |
| マスターアップ | 2028-06-30 | 430 | 1,703 | +64日 |

符号がきれいに分かれ、**計画が前半に寄りすぎていることが1列で読める**。
タスク数だけを並べた表ではこれは出てこない。

行クリックで下のグラフが連動、ダブルクリックでガントチャートタブへ移動して
そのマイルストーンで絞り込む（絞り込みは既存の `ChoiceFilterGroup` を再利用）。

> **集計上の注意**: タスクは `job_task_overrides.milestone_id` でジョブ既定と別の
> マイルストーンに付け替えられるため、**1ジョブが複数マイルストーンにまたがりうる**。
> ジョブ数列は単純合計すると総ジョブ数と一致しない。合計行では「延べ」と明記し、
> 実数はKPIタイル側を正とする。タスク数・工数はタスク単位なので重複しない。

### 3-3. チーム別サマリー

15チーム分の折れ線を1枚に重ねても読めないので二段構えにする。

1. **チーム × 月の稼働率ヒートマップ**（全チーム）。15行×28列が1画面に収まり、
   「どのチームの、どの時期が詰まっているか」が一目で分かる。単一色相の濃淡。
2. **選択チームのライン数推移**（1チーム）。使用ライン数を面、上限ライン数を
   階段の破線で重ね、`team_capacity_changes` による増減が階段として見える。

列: チーム / 上限ライン数（最大） / 割当タスク数 / 工数 / 平均稼働率 / 飽和日数 / 超過件数。

**「上限超過日数」は列に置かない。** スケジューラは上限を絶対の制約として扱い、
超えるくらいなら後ろへ押し出すので、この値は構造上つねに0になる（実測でも
全15チームで0日）。代わりに置くのが**飽和日数**（使用＝上限の日数）で、
これが「そのチームがボトルネックだった日数」を表す。容量不足は上限超過ではなく
**締切超過に化けて現れる**、という関係をこの2列で示す。

### 3-4. ワークフロー別サマリー

月ごとの**稼働タスク数**（その月に1日でも走っているタスク）を積み上げ面グラフに
する。開始タスク数ではなく稼働タスク数にするのは、長いタスクが月をまたぐときに
山が消えてしまうため。

列: ワークフロー / ジョブ数 / タスク数 / 工数 / リードタイム中央値 / 超過件数。
リードタイムは「1ジョブの最初のタスク開始〜最後のタスク終了」の中央値
（平均だと外れ値のジョブに引っ張られる）。

色はワークフロー・チームとも既存の `_TEAM_COLOR_PALETTE`（12色・順序固定）を
そのまま使う。タブをまたいだときの読み替えコストを消すため。ただしサンプルは
チームが15あり13番目以降は無彩色に潰れる——ヒートマップを色ではなく
**単一色相の濃淡**にしてあるのは、この制約を回避するためでもある。

### 3-5. 要注意タスク

超過日数の降順で上位20件。列: ジョブ / タスク / チーム / マイルストーン /
計画終了日 / 超過日数 / 原因。「原因」は `Resource_Adjusted` と
`Constraint_Violation` から機械的に付ける短いラベル。

**ダブルクリックでジョブ作成タブへ飛ぶ。** 集計は「どこが悪いか」までしか
言えないので、サマリーを読み物で終わらせず修正の入口にする。

## 4. 「進捗割合」の定義

> **最重要の論点。このアプリは実績を一切持っていない。**
> `.pschedule` にあるのは計画データだけで、実績の取り込みは `docs/roadmap.md` §5 で
> 「外部ツールとファイルで交換する」方針として未着手のまま置かれている。
> したがって出せる「進捗」はすべて**計画から導いた値**にしかならない。

曖昧なまま「進捗62%」と書くと読んだ人は必ず実績だと受け取る。
**ラベルは「計画上の消化率」とし、基準日（as-of）を画面上に常時表示する。**

| 定義 | 計算 | 評価 |
| --- | --- | --- |
| 件数ベース | 基準日までに終わる予定のタスク数 ÷ 総タスク数 | 実装は簡単だが1日のタスクと14日のタスクを同じ1件として数えるため実態と乖離。単独では非推奨 |
| 工数ベース | 同左の工数（人日）÷ 総工数 | 物量に比例するので誤解が少ない。タスクが2値になる |
| **工数ベース＋按分（推奨）** | 完了済みは全量、進行中は「経過営業日 ÷ 総営業日」で按分 | 曲線が滑らか。EVMのPlanned Valueと同じ考え方で、**実績を入れたときEarned Valueと直接比較できる形**になる |

1・2番目は実装が軽い代わりに、後から3番目へ移すと数字が動いて
「先週と違う」という混乱を生む。**最初から3番目で入れるのが結局いちばん安い。**

この列は将来「計画」「実績」の2系統に割れる形で作る。集計関数の戻り値を
`{plan: …, actual: None}` の形にしておけば、実績が入った日に列を1本足すだけで済む。

## 5. 集計の定義

数字が信用されるかどうかが全て。定義が曖昧な列を1つでも混ぜると画面全体が疑われる。
以下は画面のツールチップにもそのまま出す。

| 用語 | 定義 |
| --- | --- |
| 工数（人日） | タスクの計画所要日数（**営業日**）の総和。本アプリは1タスク＝1ライン占有なので所要日数の合計がそのまま人日になる。暦日ではない |
| 稼働率 | （Σ 日ごとの使用ライン数）÷（Σ 日ごとの上限ライン数）。**いずれも稼働日のみ**を数え、土日・祝日・休業日と、上限が0の期間は分母から除く（除かないと「合流前のチーム」の稼働率が不当に低く出る） |
| 飽和日数 | 使用ライン数＝上限ライン数となった稼働日の数。そのチームがボトルネックだった日数 |
| スラック | マイルストーンの締切 − そのマイルストーンに属するタスクの最終終了日（暦日）。負なら間に合っていない |
| 帰属 | チーム・マイルストーンとも、上書きを解決したあとの**実効値**（`result_df` の `Team_ID` / `Milestone_ID`）を使う。ジョブ既定ではない |
| 基準日（as-of） | 既定は「今日」。計画全体が未来／過去にあると意味を持たないため日付を選べるようにする。消化率とS字カーブの縦線だけがこれに依存する |

## 6. 実装方針

### 6-1. スケジューリング結果はガントチャートタブと共有する

**構成上いちばん大きな判断。** 現在 `GanttTab` は `_result_df` と
`_computed_revision` を自分で抱え、ワーカースレッドも自前で回している
（`docs/architecture.md`「ガントチャートタブのバックグラウンド計算」）。
サマリータブが同じ作りを持つと、**同じ計算が2本走り、スレッドも2系統になる**
（大規模サンプルで1回あたり実測2.0秒）。

キャッシュ判定（`db.revision`）・ワーカー管理・結果の配布を `ScheduleCache`（仮）
として `MainWindow` が1つ持ち、`GanttTab` / `SummaryTab` がそれを購読する形へ寄せる。
既存の**「要求時点のrevisionを刻む」「実行中のワーカーを全件追跡して終了を待つ」
という2つの決定はそのまま移す**——どちらも実際の不具合から入った規約なので、
作り直すと踏み直す。

### 6-2. 先に入れておきたい小さな変更: `result_df` に `Days` 列

工数の集計に必須だが、現状の結果には入っていない。無いと集計側が
`job_task_overrides.override_days` → `workflow_tasks.default_days` の解決を
**スケジューラと二重に実装する**ことになる。

値は `_parse_tasks` が `active_tasks[…]["days"]` として既に持っており、
結果を組み立てるループ（`project_scheduler.py`）で1行足すだけで済む。

### 6-3. 集計はQt非依存の純粋関数に分ける

`gui/summary_metrics.py` を新設し、`result_df` ＋ `display` ＋ 容量・休業日を
受け取って集計済みの辞書を返す関数群を置く。描画は別。
`gui/resource_histogram.py` が「純粋関数＋描画」に分けてある前例と同じ形。

- `pytest -m scheduler`（PySide6不要）の階層でテストできる。集計の正しさは
  ウィジェットを立ち上げずに検証できるべきもの。
- 日ごとの使用ライン数は、各タスクの `[開始, 終了)` に ±1 を置いて累積和を取る
  差分法で `O(タスク数 + 日数)`。**16,230タスクの全集計が実測で0.1秒未満**
  だったので、バックグラウンド化は不要。
- 階段関数の区間化は `resource_histogram.compute_step_segments` をそのまま
  再利用できる（同関数のdocstringが、まさにこの用途を想定して汎用にしてある
  旨を書いている）。

### 6-4. 描画は QGraphicsScene を踏襲する

`gui/gantt_view.py` / `gui/resource_histogram.py` と同じ素のシーン直接描画。
棒・積み上げ面・折れ線・ヒートマップはいずれもこれで足りる。

**QtWebEngine（Plotlyを画面内に埋める案）は採らない。** `plotly` は依存に
入っているがHTML書き出し専用で、GUIには一度も持ち込んでいない。QtWebEngineを
足すと `.exe` が桁で膨らみ（`docs/packaging.md`）、「サーバー不要・ローカル完結」
の非機能要件に対しても割に合わない。

### 6-5. Undo/Redo・UI状態

ガントチャートタブと同じ**表示専用**タブなので `@undoable` の対象は増えない。
ただし `CLAUDE.md` の規約どおり `capture_ui_state()` / `restore_ui_state(state)`
は実装する（復元対象: 基準日、選択中のマイルストーン行・チーム行、各セクションの
開閉、スクロール位置）。

**基準日はDBに保存しない。** `project.distribution_ratio` はスケジューリング結果
そのものを変えるからプロジェクト設定へ格上げした値であって、基準日は結果に
影響しない表示上の状態にすぎない。保存するとスキーマを1つ進めることになり
釣り合わない。

### 6-6. エラー時の振る舞い

ガントチャートタブと同じ。未完成なプロジェクトや失敗時は**モーダルダイアログを
出さず**、タブ内に赤字で理由を出して表示をクリアする（タブ切替・Undo/Redoの
たびに自動で呼ばれる画面でダイアログを出すと、作りかけの間じゅう操作に割り込む）。

## 7. 作らないもの

「サマリー」は際限なく膨らむ画面なので、入れないものを先に決めておく。

| 項目 | 判断 | 理由 |
| --- | --- | --- |
| EVM（PV / EV / AC） | 作らない | EVもACも実績が要る。`roadmap.md` §5 より先には原理的に置けない。ただし推奨した消化率が事実上PVなので、実績が入った日に残り2本を足すだけで成立する形にはしておく |
| バーンダウン | 作らない | 計画線しか引けず片肺の図になる |
| 累積工数のS字カーブ | 作る | 同じ計画データだけで完結し「山場がいつ来るか」に答える。実績なしでも成立する |
| クリティカルパス表示 | 後回し | 有用だが、タスクごとのスラックをスケジューラから返す必要がある（ASAP・ALAPは内部にはある）。エンジン側の仕事なので別に切る |
| シナリオ（案）の比較 | 後回し | `roadmap.md` §4-2 の独立した課題。**サマリータブは「1案の断面」に徹する** |
| 編集機能 | 作らない | 表示専用を貫く。修正はジョブ作成タブへ飛ばす |

## 8. 作る順番

| 段階 | 内容 | 答えられるようになること |
| --- | --- | --- |
| 1 | `Days`列の追加 ＋ `summary_metrics.py` ＋ KPIタイル ＋ マイルストーン別の表 | 「計画は成立しているか」。**グラフを1枚も描かずに価値の大半がここで出る**——スラックの符号が並ぶだけで前半偏重は読める |
| 2 | `ScheduleCache` の抽出 ＋ チーム別の表とヒートマップ | 「いつ誰が忙しいか」。二重計算の解消もここで済ませる |
| 3 | ワークフロー別の積み上げ面 ＋ ライン数推移 ＋ S字カーブ ＋ 要注意タスク一覧 ＋ タブ間連携 | 時系列の全体像と、修正への導線 |

段階1と2の間に `ScheduleCache` の抽出を挟んでいるのは、段階1なら `GanttTab` の
結果を受け取るだけで済み、**本格的な作り替えを「表とタイルが妥当だと確認できて
から」に遅らせられる**ため。チーム別ヒートマップまで来ると、サマリータブを先に
開いたときに自前で計算を起こす必要が出て、共有が避けられなくなる。

## 9. 判断待ちの点

1. **「進捗割合」の定義** — 工数ベース＋按分（§4）を推奨。後から変えると数字が
   動くので先に決めたい。
2. **実績の扱い** — 今回は入れず、列を後から足せる形だけ用意する。実績を今回の
   スコープに含めるなら、サマリータブより先に `roadmap.md` §5 の取り込み機構が要る。
3. **ヒートマップを主役に据えてよいか** — 据えたい。15チーム×28か月が1画面に
   収まり折れ線15本より読める。ただし見慣れない図でもある。
4. **タブ名** — 「サマリー」で問題ないが実態は分析・診断寄り。既存4タブが
   動詞的（設計・作成）なので「分析」も候補。
5. **CSV / Excel書き出し** — 各表に付ける価値は高いが、`roadmap.md` §5 の進捗交換
   フォーマットと形式を揃えるべき。単純なCSVに留め、Excelは §5 と同時に設計したい。
6. **段階1だけ先に出す進め方** — 推奨。表とタイルは実データを見ないと妥当性を
   判断しにくい。
