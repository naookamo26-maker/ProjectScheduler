# サマリータブ 設計案（相談メモ）

スケジューリング結果を分析・可視化するための5番目のタブ「サマリー」の設計案。
**未実装**。着手の可否・範囲を決めるための検討メモとして残す。

数値はすべて、同梱の大規模サンプル
（`data/Project_Schedule_Sample_AAA_Large.pschedule`、1,916ジョブ / 16,230タスク /
15チーム / 10ワークフロー / 6マイルストーン）を実際にスケジューリングして得た**実測値**。

---

## 1. 前提

このメモは次の3点を前提にしている。いずれも「サマリーに何を出すか」より手前の、
**このツールが何を測る道具なのか**という定義に関わる。

1. **このツールは工数管理をしない。** スケジューリングの基礎になっている日数は
   「タスクを実行する期間」であって、実際の工数を表していない。したがって
   **人日・工数という語も指標も使わない。**
2. **状態（未着手・進行中・完了）は件数で数える。** 所要日数による重み付け・按分はしない。
3. **チームのライン数上限は既定で「指定なし」。** 計画段階で割当人数が確定していることは
   少なく、「このスケジュールを達成するには何本必要か」をシミュレーションしてから
   検討するサイクルを回す。上限を明示するのは、開発冒頭に人を入れられない・
   早めに引き上げる・一定期間だけ絞る、といった例外の表現に使う。

3つ目の帰結として、**スケジューリング結果の意味が変わる**。上限がある世界では結果は
「与えられた人数でいつ終わるか」だが、上限が無い世界では結果は
**「この日程を守るには何本のラインが要るか」**になる。サマリータブは後者を出す画面になる。

同時に、**稼働率・飽和日数・上限超過日数といった「上限を分母や基準に取る指標」は
成立しなくなる**ので、指標の一覧から外す。

## 2. 検証：上限を外すと何が起きるか

同梱の大規模サンプルを、上限ありの現状と、全チームの上限を外した場合とで組み直して比べた。

| | 上限あり（現状） | 上限なし | 意味 |
| --- | ---: | ---: | --- |
| 締切超過タスク | 413件（最大113日） | **0件** | この計画の遅れは**100%が人手不足由来**。依存の鎖が締切に入らないタスクは1件も無い |
| リソース調整 | 1,686件 | 0件 | 押し出しが起きないので `Resource_Adjusted` は常にFalseになる |
| 計画終了日 | 2028-04-27 | 2028-04-27 | 末尾は変わらない（最後のタスクは依存で決まっている） |
| 計算時間 | 2.0秒 | 2.3秒 | 上限なしでも現行実装のまま問題なく完走する |

### 2-1. 締切超過が2種類に割れる

この比較から、締切超過を機械的に2つに分類できる。対処法が正反対なので、
**サマリータブでは必ず分けて表示する。**

- **人を足せば解消する超過** — 上限なしで再計算すると消えるもの。増員・期間の前倒しで解決しうる。
- **人を足しても解消しない超過** — 上限なしでも残るもの。依存の鎖そのものが締切に入っていない。
  **増員では絶対に解決しない。**締切を動かすか、タスクを分割・短縮するか、依存を切るしかない。

判定は「上限を外して1回余分に計算し、超過が残るか」だけで付く（実測2.3秒）。
今回のサンプルは前者が413件、後者が0件だった。

### 2-2. 必要ライン数は配置比率に強く依存する

**今回いちばん重要な発見。** 上限を外したうえで `project.distribution_ratio`
（ガントチャートタブの「配置コントロール」）を振ると、必要ライン数の合計ピークはこう動く。

| 配置比率 | 0.00 | 0.30 | 0.50 | 0.65 | 0.70 | 0.75 | **0.80** | 0.90 | 1.00 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 必要ライン数（合計ピーク） | 1,916 | 474 | 344 | 270 | 256 | 253 | **244** | 306 | 524 |

最速（0.0）に寄せると全1,916ジョブの先頭タスクが一斉に走り出して1,916本、
ギリギリ（1.0）に寄せると締切直前に固まって524本、その間の0.8付近で最小の244本になる。
**8倍近い開きがある。**

つまり**「このプロジェクトには何人必要か」という問いは、配置比率を決めないと答えが定まらない。**
逆に言えば、比率を振ってこの曲線を描くこと自体が「何人必要かをシミュレーションしてから
検討する」サイクルそのものになる。実装は上限を外した計算を数点ぶん回すだけで、
1点2.3秒なので11点で25秒。バックグラウンドで回してよい。

### 2-3. 合計値だけを見てはいけない

比率0.7での**合計**必要ピークは256本で、サンプルに設定されている**合計**上限ピーク281本より
少ない。合計だけ見ると「足りている」と読める。しかし**チーム別に見ると15チーム全部が不足**
している（+2〜+13本）。各チームのピーク時期がずれているため、合計のピークは個々のピークの
和にならない。**合計値のKPIには必ず「不足しているチーム数」を併記する。**

## 3. 画面構成

既存4タブの流儀（縦積み・`QGroupBox`・`CollapsibleSection`・表示専用）を踏襲する。

```
[ツールバー] 基準日 / 配置比率 / 「上限なしの必要ライン数を重ねる」トグル   [表をコピー] [CSV]
[KPIタイル ×6]
[QGroupBox] マイルストーン別サマリー       … 表 + 状態3区分の積み上げ棒（件数）
[QGroupBox] チーム別サマリー — 必要ライン数 … チーム別スパークライン + 表 + 選択チームの拡大表示
[QGroupBox] ワークフロー別サマリー         … 積み上げ面グラフ（稼働タスク件数）+ 表
[QGroupBox] 要注意タスク（締切超過 上位）
```

### 3-1. ヘッドライン（KPIタイル）

6枚まで。**必要ライン数を主役のタイルに置く。**

規模（ジョブ件数 / タスク件数）／ 計画期間 ／ **必要ライン数の合計ピークとその時期** ／
**上限が足りていないチーム数** ／ 締切超過（件数・最大日数・うち増員で解消しない件数）／
開始固定日の違反。

「全体稼働率」は置かない。上限が既定で無い以上、分母が存在しないため。

### 3-2. マイルストーン別サマリー

列: 締切日 / 残日数 / ジョブ件数 / タスク件数 / 完了・進行中・未着手の件数 /
最終終了日 / スラック / 超過件数 / 判定。**工数の列は無い。**

**主役はスラック列**（締切 − そのマイルストーンに属するタスクの最終終了日）。実測値:

| マイルストーン | 締切 | タスク件数 | スラック |
| --- | --- | ---: | ---: |
| ヴァーティカルスライス | 2026-06-30 | 1,478 | **−113日** |
| ファーストプレイアブル | 2026-12-18 | 3,334 | **−57日** |
| アルファ | 2027-06-30 | 4,445 | **−23日** |
| ベータ | 2027-12-17 | 4,195 | +31日 |
| コンテンツロック | 2028-03-31 | 2,348 | +35日 |
| マスターアップ | 2028-06-30 | 430 | +64日 |

符号がきれいに分かれ、計画が前半に寄りすぎていることが1列で読める。

状態の3区分は積み上げ棒に出す。**件数のまま積む**——タスクの長短で重みを付けた瞬間に
工数の言い換えになるため。実績を持たせた後は、同じ行に「計画」「実績」の2本を並べる。

> **集計上の注意**: タスクは `job_task_overrides.milestone_id` でジョブ既定と別の
> マイルストーンに付け替えられるため、**1ジョブが複数マイルストーンにまたがりうる**。
> ジョブ件数列は単純合計すると総ジョブ件数と一致しない。合計行では「延べ」と明記し、
> 実数はKPIタイル側を正とする。タスク件数はタスク単位なので重複しない。

### 3-3. チーム別サマリー — 必要ライン数

**1チーム1枚のスパークラインを並べる。** 各スパークラインは3層を重ねる。

1. **塗り** ＝ 現在の計画での同時タスク数（上限を設定していればそれを守った結果）
2. **実線** ＝ 上限を外した場合に必要な本数。**上限を超えている区間が、そのまま
   「足りていない量」として見える**
3. **破線** ＝ 設定上限。**上限が「指定なし」のチームでは描かない**——線が無いこと自体が
   「まだ人数を決めていない」ことの表示になる

表の列: チーム / 上限設定 / 必要ピーク / 不足 / ピーク時期 / タスク件数 / 超過件数。
実測では15チーム全部が不足しており、テクニカルアート +13、QA +12、VFX +12 と続く。

**「稼働率」「飽和日数」「上限超過日数」は置かない。** 前2つは上限を分母・基準に取る指標で
上限が既定で無い設計と噛み合わず、3つ目は上限を守って計画する限り構造上つねに0になる
（実測でも全15チームで0日）。代わりに置くのが**「上限を外したときに必要な本数と、
設定上限との差」**で、これが実際に意思決定に使える量になる。

### 3-4. ワークフロー別サマリー

月ごとの**稼働タスク件数**（その月に1日でも走っているタスクの件数）を積み上げ面グラフに
する。開始件数ではなく稼働件数にするのは、長いタスクが月をまたぐときに山が消えるため。

表: ワークフロー / ジョブ件数 / タスク件数 / ジョブ所要期間の中央値 / 超過件数。
所要期間は「1ジョブの最初のタスク開始〜最後のタスク終了」の暦日で、**足し合わせずに
中央値だけを見る**——パイプラインの長さの比較に使う量であって、量の集計ではない。

色はワークフロー・チームとも既存の `_TEAM_COLOR_PALETTE`（12色・順序固定）を使う。
タブをまたいだときの読み替えコストを消すため。

### 3-5. 要注意タスク

超過日数の降順で上位20件。列: ジョブ / タスク / チーム / マイルストーン / 計画終了日 /
超過日数 / 原因。**「原因」は §2-1 の2分類**を機械的に付ける。
ダブルクリックでジョブ作成タブへ飛び、修正の入口にする。

## 4. 集計の定義

| 用語 | 定義 |
| --- | --- |
| 件数 | タスクの本数。**所要日数で重み付けしない。**このタブの唯一の「量」の単位 |
| 同時タスク数 | ある日にそのチームで走っているタスクの本数。現在の計画から数える |
| 必要ライン数 | 全チームの上限を外して同じ日程条件で組み直したときの同時タスク数。**「この日程を守るには何本要るか」**。配置比率に依存するので、値は必ず比率とセットで表示する |
| 不足 | 必要ライン数のピーク − 設定上限。上限が「指定なし」のチームでは空欄 |
| スラック | マイルストーンの締切 − そのマイルストーンに属するタスクの最終終了日（暦日） |
| 状態 | 未着手 / 進行中 / 完了 の3区分、**件数**。実績を持つ前は「基準日時点で計画上どの状態か」を同じ区分で数える（計画値であることを画面上で明示する） |
| 所要期間 | 1ジョブの最初のタスク開始〜最後のタスク終了（暦日）。**合計は取らず中央値だけを見る** |
| 帰属 | チーム・マイルストーンとも、上書きを解決したあとの**実効値**（`result_df` の `Team_ID` / `Milestone_ID`） |
| 基準日（as-of） | 既定は「今日」。状態の3区分だけがこれに依存する |

**意図的に持たない指標**: 工数・人日（所要日数の総和）、稼働率、飽和日数、上限超過日数、
加重した進捗率。前2つは「日数＝期間であって工数ではない」という前提に反し、
後3つは「上限が既定で存在する」ことを前提にした指標のため。

## 5. 懸念点

ライン数上限を既定で「指定なし」にする変更は、サマリータブより**射程が広い**。
**1〜3はサマリータブより先に片付けたほうがよい。**

### 5-1. スキーマ変更が必要になる（v15）

`teams.max_lines` は現在 `NOT NULL CHECK (max_lines >= 0)`、
`team_capacity_changes.lines` も同様。「指定なし」を表すには**NULL許容**にする必要がある。
意味は3状態になる。

- **NULL＝指定なし**（上限を設けない。既定）
- **0＝稼働なし**（その期間はチームが動かない。既存の意味を維持）
- **N＝N本**

0とNULLが別の意味を持つので、UIでも区別して見せる必要がある
（`widgets_common.py` の `DefaultAwareSpinBox` / `OptionalDateEdit` が同種の前例）。

既存ファイルの移行では、**入っている値をNULLに書き換えてはいけない**——
「意図して設定した本数」と「既定値のまま放置された本数」を区別する情報が無いため。

`CLAUDE.md` の規約により、スキーマ変更は**全テスト（210件）実行の対象**になる。

### 5-2. `Resource_Adjusted` と `ResourceOverflowError` が既定構成で意味を失う

上限が無ければ押し出しが起きないので `Resource_Adjusted` は常にFalseになる
（実測 1,686件 → 0件）。`ResourceOverflowError` も発生しなくなる。

影響はサマリータブの外に出る。**ガントチャートタブの「リソース調整あり」のツールチップ
表示と、リソース調整率という指標が、既定構成では常に空になる。**
廃止ではなく「上限を設定しているチームがある場合にだけ意味を持つ表示」として
位置づけ直すのが妥当だと考えるが、仕様判断が要る。

### 5-3. 基本情報設定タブのリソースヒストグラムの前提が崩れる

あのグラフは「計画上の同時ライン数**の上限**の推移」を描いている
（`gui/resource_histogram.py`）。上限が既定で指定なしになると、
**多くのプロジェクトで描くものが無くなる。**

自然な発展先は**「必要ライン数を重ねる」**——同ファイルのdocstringが
「将来ガントチャートタブで実際のタスク使用数を表示する用途に使い回せるよう」
計算を2段に分けてある、と書いている拡張にあたる。ただし基本情報設定タブは
**入力タブでスケジューリング結果を持たない**ので、結果の共有（§6-1）が前提になる。

### 5-4. 新規チームの既定値も変わる（これは改善）

現在「＋チーム」は**ライン数1**でチームを追加する（`docs/screens.md`）。
1本は極めて厳しい制約で、初めて使う人はチームを作った瞬間に全タスクが直列に伸びるが、
理由が画面から分からない。既定を「指定なし」にするとこの落とし穴も同時に消える。

### 5-5. 「必要ライン数」は最小人数の証明ではない

比率を振って得られる最小値（実測244本）は、**スライダーで表現できる配置の中での最小**
であって、「理論上これ以下では不可能」という下界ではない。個々のタスクを独立に
前後させれば、もっと平らな配置が存在しうる（山積み最小化は本来もっと重い最適化問題）。

画面上の表現も**「この配置なら244本で足りる」**に留め、「最低244人必要」とは書かない。

### 5-6. 計算が2本になる

「必要ライン数」を出すには**上限ありと上限なしの2回**スケジューリングする
（2.0秒 + 2.3秒）。比率スキャンまで出すならさらに数点ぶん。

`ScheduleCache`（結果のキャッシュとワーカー管理を `MainWindow` に集約し、
ガントチャートタブと共有する案）は、この変更で**必要性が上がる**。ただし
上限なしの計算は**遅延させる**——サマリータブを開いたとき、または比較トグルを
オンにしたときだけ走らせれば、ガントチャートタブしか使わない利用者に負担が出ない。

比較の妥当性は確認済み。上限を外してもASAP／ALAPは変わらない（どちらも容量に
依存しない計算のため）ので、2つの結果は**同じ基準点に対する配置違い**として
素直に比較できる。実測でも計画終了日は 2028-04-27 で一致した。

### 5-7. 合計値が誤解を生む

§2-3のとおり。KPIタイルに合計値だけを大きく出すと「足りている」と読まれるので、
**必ず「不足しているチーム数」を併記する。**

## 6. 実装方針

### 6-1. スケジューリング結果はガントチャートタブと共有する

現在 `GanttTab` は `_result_df` と `_computed_revision` を自分で抱え、ワーカースレッドも
自前で回している（`docs/architecture.md`「ガントチャートタブのバックグラウンド計算」）。
サマリータブが同じ作りを持つと同じ計算が2本走る。キャッシュ判定（`db.revision`）・
ワーカー管理・結果の配布を `ScheduleCache`（仮）として `MainWindow` が1つ持ち、
`GanttTab` / `SummaryTab` が購読する形へ寄せる。

既存の**「要求時点のrevisionを刻む」「実行中のワーカーを全件追跡して終了を待つ」
という2つの決定はそのまま移す**——どちらも実際の不具合から入った規約なので、
作り直すと踏み直す。

### 6-2. `result_df` への `Days` 列追加は不要

初版では工数集計のために必要としていたが、件数と同時タスク数しか使わなくなったので
`Start_Date` / `End_Date` だけで足りる。`project_scheduler.py` に手を入れずに済む。

### 6-3. 集計はQt非依存の純粋関数に分ける

`gui/summary_metrics.py` を新設し、結果と表示情報を受け取って集計済みの辞書を返す
関数群を置く。描画は別。`gui/resource_histogram.py` の「純粋関数＋描画」と同じ形。

- `pytest -m scheduler`（PySide6不要）の階層でテストできる
- 同時タスク数は各タスクの `[開始, 終了)` に ±1 を置いて累積和を取る差分法で
  `O(タスク数 + 日数)`。**16,230タスクの全集計が実測0.1秒未満**なので、
  集計自体のバックグラウンド化は不要（重いのはスケジューリング側）
- 上限の階段線は `resource_histogram.compute_step_segments` をそのまま再利用できる

### 6-4. 描画は QGraphicsScene を踏襲する

`gui/gantt_view.py` / `gui/resource_histogram.py` と同じ素のシーン直接描画。
スパークライン・積み上げ面・棒はこれで足りる。**QtWebEngine（Plotlyを画面内に埋める案）
は採らない**——`plotly` はHTML書き出し専用で、足すと `.exe` が桁で膨らみ
（`docs/packaging.md`）、「サーバー不要・ローカル完結」の非機能要件に対しても割に合わない。

### 6-5. Undo/Redo・UI状態

表示専用タブなので `@undoable` の対象は増えない。ただし `CLAUDE.md` の規約どおり
`capture_ui_state()` / `restore_ui_state(state)` は実装する（基準日・選択行・
セクション開閉・スクロール位置）。基準日はDBに保存しない（結果に影響しない表示状態のため）。

### 6-6. エラー時の振る舞い

ガントチャートタブと同じ。未完成なプロジェクトや失敗時は**モーダルダイアログを出さず**、
タブ内に赤字で理由を出して表示をクリアする。

前提の変更のほうが射程が広いので、サマリータブは3番目以降になる。

| 1 | ライン数上限のNULL許容（スキーマv15）＋ 基本情報設定タブのUI ＋ 新規チームの既定を「指定なし」に | サマリータブの中身がこの意味論の上に乗る。**先に決まっていないと、作った指標を作り直すことになる** |
| 2 | 上限なしでの再計算と、`Resource_Adjusted` 系表示の位置づけ直し | 「必要ライン数」と「締切超過の2分類」の土台。ガントチャートタブ側の表示にも影響する |
| 3 | `summary_metrics.py` ＋ KPIタイル ＋ マイルストーン別の表（状態3区分を含む） | グラフを1枚も描かずに価値の大半が出る |
| 4 | `ScheduleCache` の抽出 ＋ チーム別の必要ライン数（スパークライン＋拡大表示） | 二重計算の解消と、いちばん見たい図。基本情報設定タブのヒストグラム拡張もここに乗る |
| 5 | ワークフロー別の積み上げ面 ＋ 要注意タスク一覧 ＋ タブ間連携 | 時系列の全体像と、修正への導線 |
| 6 | 配置比率スキャン（必要ライン数の曲線） | 単独で価値があるが、他が動いてからでよい |

## 8. 判断待ちの点

1. **0とNULLの区別** — NULL＝指定なし、0＝稼働なし、N＝N本 の3状態にする案。0を
   「稼働なし」として使う既存の用法（遅く合流するチーム）を壊さないため。UI上の
   見え方は要検討。
2. **上限を「制約」として扱い続けるか** — 続ける案。上限を設定したチームでは
   これまでどおり超えないよう押し出す。「超えたかどうか」は、上限を外した場合の
   必要本数を重ねて見せることで表現する（上限を破って配置すると、ガントチャートが
   実行不可能な計画を描くことになるため）。
3. **状態の粒度** — タスク単位に持ち、ジョブの進捗は「完了タスク件数 ÷ 総タスク件数」の
   派生とする案（ジョブに独自の状態を持たせない）。二重管理を避けるため。
4. **実績前の「計画上の状態」を出すか** — 出す案。ただし計画値であることを明示する。
5. **配置比率スキャンを入れるか** — 入れたい。「何人必要かをシミュレーションしてから
   検討する」サイクルに最も直接対応する機能。優先度は最後でよい。
6. **タブ名** — 実態が「必要リソースのシミュレーション」に寄ったので、「サマリー」より
   「分析」のほうが合うかもしれない。
