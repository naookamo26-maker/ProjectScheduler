# 今後の検討事項（設計メモ）

大規模プロジェクトへの対応を検討する中で洗い出した、未着手の課題と設計方針を
記録しておく。実装済みの内容は `docs/architecture.md` を参照。

このメモは「何をやるか」よりも **「なぜその形にするか」「なぜ他の形にしないか」**
を残すことを目的にしている。数値はすべて、同梱の大規模サンプル
（`data/Project_Schedule_Sample_AAA_Large.pschedule`、1,916ジョブ / 16,230タスク）
での実測値。

---

## 1. 現在地

大規模プロジェクトへの対応として、次の4点は対応済み（PR #19 / #20）。

| # | 項目 | 結果 |
|---|---|---|
| 1 | 優先度(Priority)がリソース競合時に反転していた不具合の修正 | 押し出され率が 高優先度0.4% / 低優先度5.8% と正しい順序になった |
| 2 | 締切超過をエラーではなく結果（`Deadline_Overrun_Days`）として返す | 1タスクの超過で全体の日程が得られなくなる状態を解消 |
| 3 | スケジューリングの高速化（`_WorkCalendar` 他） | 16,000タスクで 6.61s → 0.58s |
| 4 | ガントチャートタブのバックグラウンド計算・ジョブ一覧の遅延生成 | タブ切替 18.72s → 0.22s、ファイルを開く 9.74s → 0.72s |

これにより、16,000タスク規模でも一通りの操作が待たされずに行える状態になっている。

## 2. 残っているスケール課題

### 2-1. ジョブ間依存リンクの追加が件数の2乗（優先度: 中）

`ProjectDatabase.add_job_dependency_link()` は1件追加するたびに
`sync_dependency_templates()` を呼び、**その時点の全リンクを走査し直す**。
リンクをN件張るとO(N²)になる。

大規模サンプルの生成（558リンク）で実際に踏んだため、
`scripts/generate_large_sample.py` では「行を先に挿入してから最後に1回だけ
`sync_dependency_templates()` を呼ぶ」形で回避している。GUIから多数のリンクを
張る場合（依存先ジョブをまとめて追加するダイアログ）は同じ問題が出る。

**対策案**: 影響するリンクだけを同期する版（`sync_dependency_templates(link_ids=...)`）
を用意するか、複数リンクをまとめて登録して最後に1回同期する一括登録APIを足す。
全同期は「想定外の経路でズレた場合の保険」という位置づけなので、リンク追加の
たびに全件を舐める必要は本来ない。

### 2-2. HTMLガントチャートの閲覧性（優先度: 中）

16,230タスクでHTML出力は9.6MB。**出力にかかる時間（約2.2秒）は問題ではない**が、
ブラウザ側で16,000本のバーを描画・操作するのが重い。

**対策案**: 既定をジョブ単位のロールアップ（1ジョブ1バー、期間はタスクの
最早開始〜最遅終了）にして、クリックでタスク単位へドリルダウンする。
チーム別の色分けは、ジョブ内で最も多いチームか、複数チームなら中間色にする等の
整理が要る。

### 2-3. ガントチャートタブの残り2.8秒（優先度: 低）

タブ切替が2.8秒かかる。スケジューリング本体は0.68秒でワーカースレッドに逃がして
あるため、残りはGUIスレッド側の `build_frames()` / `build_display()`（DBの読み出しと
DataFrameの組み立て）と、QGraphicsSceneの構築が占める。

**対策案**: `build_frames()` の結果も `ProjectDatabase.revision` でキャッシュする。
シーン構築は表示中のワークフロー1件分しか作っていないため、これ以上詰めるなら
描画側（ラベルのアイテム数削減など）の話になる。

### 2-4. Undoのメモリ（対応不要と判明）

当初「大規模プロジェクトではUndo段数が黙って減るのでは」と懸念していたが、実測では
スナップショット1件あたり **0.34MB**、上限128MBで **約186操作分**、1操作の記録に
4msだった。ワークフローがテンプレート（ジョブ数に比例しない）であるためDB自体が
小さく収まっており、当面は対応不要。

## 3. エンジン・データモデルの機能不足

### 3-1. 依存関係のラグ・種別（優先度: 高／実装コスト: 小）

現在の依存関係は **FS（Finish-to-Start）・ラグ0のみ**。実務では次が欲しくなる。

- 「レビュー期間を2日空けてから次工程」＝ FS + lag
- 「7割できたら次に着手」＝ SS（Start-to-Start）+ lag

`task_dependencies` に `lag_days INTEGER NOT NULL DEFAULT 0` と
`dep_type TEXT NOT NULL DEFAULT 'FS'` を足す。ラグだけなら実装は
`_calc_asap_dates` / `_calc_raw_dates` / `_run_leveling` の3箇所に加算を入れるだけで、
**残課題の中では最も費用対効果が高い**。

### 3-2. 祝日を稼働日に戻せない（優先度: 中／実装コスト: 小）

`_WorkCalendar` は日本の祝日を無条件に休業日として扱い、`holidays` テーブルは
休業日の**追加**しかできない。以下が表現できない。

- 祝日出勤（繁忙期の休日稼働）
- 法改正による祝日の移動（五輪年の移動祝日のような例外）

**対策案**: `holidays` に `is_working_day INTEGER NOT NULL DEFAULT 0`（1なら
「例外的に稼働する日」）を足し、`_WorkCalendar` の構築時に祝日マスクより後に
適用する。

### 3-3. スケジュールの安定性（優先度: 中／外部連携の前提）

`_job_ratio_jitter()` はジョブIDのハッシュで分散量を決めているため、内部IDが
変われば日程が動く。また、入力を少し変えるだけでスケジュール全体が
入れ替わりうる（グリーディな1パス方式なので当然ではある）。

これは単体では実害が小さいが、**外部タスク管理システムと同期し始めると効いてくる**。
小さな編集で数千タスクの日程が総入れ替えになると、外部システムとの差分が
意味を持たなくなり、更新通知も大量に飛ぶ。

**対策案**: 「前回の結果を初期解として尊重する」モードを設ける。前回配置と
同じ日程が取れるならそこを優先し、取れない場合だけ動かす。§4-1の
`task_constraints` があれば、前回結果を `START_ON` 制約として与える形でも近い
ことができる。

### 3-4. タスクの分割・中断（優先度: 低／明文化のみで可）

現在のモデルでは、タスクは**連続した営業日ブロックを1ラインで占有**し、
中断・分割・プリエンプションを表現できない。実績を取り込むと「着手したが
止まっている」状態は必ず出る。

無理に対応する必要はないが、**モデルの制約として明文化しておくべき**
（実績反映の設計時に必ず論点になる）。

## 4. 「試す」ための仕組み

「このタスクを前倒ししたらどうなるか」「このタスクはもっと後ろでもいいのでは」
を試せるようにする。

### 4-1. `task_constraints`（制約）の導入（優先度: 高）

**日付を直接データとして持たせてはいけない。** タスクに `start_date` を入力として
持たせると、計算結果と入力が同じ列に混ざり、依存関係・所要日数・休業日を変えた
瞬間に矛盾する。整合性を保つコードが際限なく増える。

代わりに **制約（constraint）として別テーブルに持つ**（MS Projectの制約と同じ考え方）。

```sql
CREATE TABLE task_constraints (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    job_id           INTEGER NOT NULL REFERENCES jobs(id) ON DELETE CASCADE,
    workflow_task_id INTEGER REFERENCES workflow_tasks(id) ON DELETE CASCADE, -- NULL = ジョブ全体
    kind TEXT NOT NULL CHECK (kind IN ('SNET','SNLT','FNLT','START_ON')),
    date TEXT NOT NULL,
    note TEXT NOT NULL DEFAULT '',
    UNIQUE(job_id, workflow_task_id, kind)
);
```

- `SNET`（Start No Earlier Than）＝ この日以降に開始 ＝ **後ろ倒し**
- `SNLT`（Start No Later Than）＝ この日までに開始
- `FNLT`（Finish No Later Than）＝ この日までに終了 ＝ 個別締切
- `START_ON` ＝ 固定（ピン留め・実績確定・外部都合）

**守るべき不変条件はひとつだけ**:

> 制約は入力、日付は出力。この分離を絶対に崩さない。

制約は「解が満たすべき条件」であって「解」ではない。だから依存関係を足しても
休業日を変えても制約データ自体は壊れない。壊れるのは「解が見つからない」場合
だけで、それは**別途の整合性維持ロジックではなく、スケジューリング実行時に
自然に検出される診断結果**として扱う（締切超過と同じ扱い方、§1の2）。

制約が0件でも成立するため既存データは無変更、参照整合性は外部キーだけで済む。
現在GUI側に散らばっているマイルストーン整合ロジック
（`cascade_milestone_to_successors` 等）のような「入力同士を事前に矛盾させない
ためのコード」を増やさずに済むのが最大の利点。

**実装上の要点（ここが設計の肝）**

1. **制約はASAP・ALAP両方の伝播に入れる。** `SNET` を `_calc_asap_dates` の下限に、
   `FNLT` を `_calc_raw_dates` の上限に織り込まないと、後続タスクのスラック計算が
   ずれる。
2. **固定タスクを先にブッキングする2パス構成にする。** 現在はトポロジカル順に
   処理するため、固定タスクの番が来たときには既にその時間帯のラインが埋まっていて
   置けない。「固定／準固定を先に予約 → 残りを平準化」に分ける。

**この2パス構成は §5 の実績反映でまったく同じものが必要になる。**
ここを一本の仕組みとして設計するのが、全体で最も効く判断。

### 4-2. シナリオ（案）の比較（優先度: 中）

「前倒ししたらどうなるか」で本当に欲しいのは、①ベースラインを保ったまま
②差分を当てた別案を計算し ③**並べて差分を見る**、という流れ。段階を踏む。

- **段階0（実装ほぼゼロ）**: ガントチャートタブで `distribution_ratio` 等をその場で
  変えて再計算し、結果に名前を付けて保持して次の結果と比較する。これだけで
  「試す」体験の大半が得られる。
- **段階1**: `task_constraints` をベースラインに直接導入する（シナリオ無し）。
- **段階2**: `scenarios` テーブルを入れ、制約とパラメータ上書きを紐付ける。

`job_task_overrides` が既に「差分のみ保持」という思想で作られているので、
その考え方を素直に拡張できる。**シナリオを持つ意味は比較にある**ので、
`result_df` 同士を `Job:Task` キーで結合した差分表示（何日動いたか、締切超過が
増減したか、チーム別の負荷ピークがどう変わったか）を必ずセットで作ること。
`gui/resource_histogram.py` は流用できる設計になっている。

## 5. 進捗の外部連携

計画を外部のタスク管理システム（Redmine等）へ書き出し、実績を取り込んで
「当初計画とのズレ」「現状からの再計画」を見られるようにする。

### 5-1. 基本方針: 計画と進捗記録のツールを分ける

本アプリが日々の実績入力まで抱えると、毎日使われるツールになりUI要求が跳ね上がる
（通知・権限・コメント・添付…）。本アプリは **「計画と再計画のエンジン」** に
集中し、進捗の記録は外部に任せるのが良い。

### 5-2. 最初はファイル（Excel）で作る。API直結を先に作らない

理由:

- Redmine以外（Jira / Backlog / スプレッドシート）へも展開できる
- **「サーバー不要・ローカル完結」という非機能要件を壊さない**
  （`.pschedule` にAPIキーを保存する、という面倒を先送りできる）
- テストが書ける

```
Redmine API ─┐
Excel ───────┼→ 中間形式（進捗レコード）→ progress_snapshots → 再計画
CSV/JSON ────┘
```

**Excelを選ぶ積極的な理由**: データ検証（ドロップダウン）・条件付き書式・
シート保護が使えるため、「壊れた入力」を構造的に減らせる。CSVには無い武器で、
本アプリの非機能要件「ミスの構造的防止」と同じ思想。`openpyxl` は既に依存にある。

**旧Excel（廃止済み）とは別物**であることに注意（`docs/requirements.md` の
「対象外」も参照）。

| | 旧Excel（廃止した） | 新Excel（この案） |
|---|---|---|
| 目的 | 計画の入力（マスタデータ） | 進捗の交換（実績） |
| 構造 | 8シートがID（`WF_CHAR`、`JOB:TASK`）で相互参照 | 1行1タスクのフラットな表 |
| 人が触る所 | 全部（依存関係・チーム・日数・ID） | 状態・実績日・残日数だけ |

廃止理由（IDのタイプミス、参照ミス、依存関係の全体像が掴めない）は、進捗交換には
1つも当てはまらない。

### 5-3. シート構成案

- **`進捗入力`** — 1行1タスク
  - 隠し＋保護: `Key`（`JOB_003:T_012` 相当の安定キー）
  - 参照用（読み取り専用・**書き戻さない**）: ジョブ名 / タスク名 / チーム /
    マイルストーン / 計画開始日 / 計画終了日 / 計画日数
  - 入力列（**書き戻す**）: 状態（未着手・進行中・完了・中止）/ 実績開始日 /
    実績終了日 / **残日数** / 備考
- **`メタ`** — `as_of_date` / 書き出し日時 / スキーマバージョン / 書き出し元のハッシュ
- **`凡例`** — 入力ルール

### 5-4. 取り込み時の検証

必ず **プレビュー → 確認 → 適用**（Undo 1単位）とする。

- スキーマバージョン照合、書き出し元ハッシュで「どの書き出しに対する回答か」を照合
- **キーが無い／不明な行は黙って無視せず、一覧で提示する**
- 状態と日付の整合（完了なのに実績終了日が空、`as_of_date` より未来の実績日 等）

### 5-5. 必ず踏む3つの論点（Redmineでも形を変えて出る）

1. **同一性の維持** — Excelは行が並べ替えられ、コピペされ、挿入・削除される。
   **名前でのマッチングは絶対にやらない。** 隠し列の安定キーだけで突き合わせる。
   一度書き出したタスクの内部IDは再利用・再生成しない（＝削除ではなく無効化を
   徹底する。`is_active` の思想は既にある）。
2. **正／従の線引き** — 最初に決めないと必ず破綻する。**片方向push（計画）＋
   片方向pull（実績）に割り切る。**

   | 項目 | 正 |
   |---|---|
   | タスクの存在・構造・依存関係 | **本アプリ** |
   | 見積日数・担当チーム・優先度 | **本アプリ** |
   | 計画開始日／終了日 | **本アプリ**（シミュレーション結果） |
   | 実績開始日・実績終了日・状態・残作業 | **外部システム** |

   双方向で同じフィールドを編集可能にすると、コンフリクト解決を作る羽目になり
   コストが跳ね上がる。「外部で計画日を動かしても取り込まない（ただし"計画と
   違う"という差分としては見える）」が正しい割り切り。

   **ここを曖昧にすると「Excelで日数を直したのに反映されない」というクレームに
   なり、結局双方向同期を作る羽目になる。** 計画列はシート保護と凡例で
   「編集しても反映しない」ことを明示する。
3. **粒度（1:1を前提にしない）** — 「1タスクを3人で分担 → 外部では3チケット」は
   普通に起きる。`external_links` は `local_id : external_id` が 1:N を許す形に
   しておく。取り込み時は「子が全部閉じたらタスク完了、残日数は合計」という
   集約ルールを持つ。最初から1:1前提のスキーマにすると必ず作り直しになる。

   逆に「外部にあるが本アプリに無い」突発作業も必ず発生する。これを
   取り込めるようにしておくと価値が高い（＝計画外作業がチームのキャパシティを
   食っている、という可視化になる）。

### 5-6. 保持すべきデータ

**最重要は `as_of_date`（基準日）。** これが無いと実績データは何の意味も持たない。
全ての実績スナップショット・全ての計算結果に必須。

```sql
CREATE TABLE progress_snapshots (       -- 取り込んだ実績（時系列で残す）
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    as_of_date TEXT NOT NULL, source TEXT NOT NULL, imported_at TEXT NOT NULL
);
CREATE TABLE progress_task_status (
    snapshot_id INTEGER NOT NULL REFERENCES progress_snapshots(id) ON DELETE CASCADE,
    job_id INTEGER NOT NULL, workflow_task_id INTEGER NOT NULL,
    status TEXT NOT NULL,               -- not_started | in_progress | done | cancelled
    actual_start TEXT, actual_finish TEXT,
    remaining_days REAL,                -- ★ 進捗率より圧倒的に重要
    percent_done REAL, spent_hours REAL, note TEXT
);

CREATE TABLE schedule_runs (            -- 計算結果のスナップショット
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    label TEXT, scenario_id INTEGER, as_of_date TEXT,
    computed_at TEXT NOT NULL, params_json TEXT NOT NULL,
    is_baseline INTEGER NOT NULL DEFAULT 0
);
CREATE TABLE schedule_run_tasks (
    run_id INTEGER NOT NULL REFERENCES schedule_runs(id) ON DELETE CASCADE,
    job_id INTEGER, workflow_task_id INTEGER,
    start_date TEXT, end_date TEXT, team_id INTEGER,
    milestone_id INTEGER, resource_adjusted INTEGER, overrun_days INTEGER
);

CREATE TABLE external_links (           -- 外部システムとの対応（1:N可）
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    local_kind TEXT NOT NULL,           -- 'job' | 'job_task'
    job_id INTEGER, workflow_task_id INTEGER,
    system TEXT NOT NULL,               -- 'redmine' | 'excel' 等
    external_id TEXT NOT NULL, external_url TEXT,
    status TEXT NOT NULL DEFAULT 'active',  -- active | missing | detached
    last_synced_at TEXT, last_pushed_hash TEXT
);
```

**`remaining_days`（残り所要日数）を第一級で持つこと**を強く勧める。
「80%完了」は残り2割を意味しない。`done_ratio` しか取れない場合は
`remaining = ceil(days × (1 - ratio))` で近似しつつ、**手で上書きできる**ように
しておく。実務ではここが一番効く。

**その他、後で効くもの**

- **休業日カレンダーの実体化** — 現在は日本の祝日をコード内の近似式で計算して
  いる（`_vernal_equinox_day` 等）。実績と突き合わせる際、「その日は稼働日
  だったか」の判定が過去に遡って一貫している必要がある。計算に使った休業日集合を
  `schedule_runs` に保存するか、祝日をテーブルとして実体化する。
- **見積の履歴** — `default_days` をいつ何から何に変えたか。実績と突き合わせると
  見積バイアスが定量化できる。
- **チームの実効キャパシティ** — `team_capacity_changes` は計画値。実績から
  「実際は何本並行していたか」を逆算してヒストグラムに重ねると、計画前提の
  妥当性が検証できる。

### 5-7. 再計画のルール

**ベースライン（当初計画）の保存が必須。** 「ズレの確認」とは
「実績 vs 現計画 vs ベースライン」の3系列比較だから。

再計画時のスケジューラ側の扱い（§4-1の2パス構成とまったく同じ形）:

- **完了タスク**: 実績日で固定。後続の下限は実績終了日
- **進行中タスク**: `actual_start` で固定、終了 = `as_of + remaining_days`（営業日換算）
- **未着手タスク**: `as_of_date` を新しい下限として通常どおり平準化
- **リソースの二重計上を避ける**: 進行中タスクは `as_of` 以降の残り期間だけ
  ラインを消費する（予約テーブルを `as_of` 以降で持つ）
- **締切超過はエラーにせず結果として返す** — 実績を入れれば締切に間に合わないのが
  普通なので、この点は §1 の2で先に手当て済み

3系列が揃うと、SPI相当の指標と **マイルストーン・トレンド・チャート**
（各 run の `as_of` を横軸、各マイルストーンの予測着地日を縦軸にプロット）が
出せる。実装は既存データをプロットするだけだが、**この種のツールで最も費用対効果の
高い可視化**だと考えている（「締切が守れそうか」ではなく「守れなくなりつつあるか」
が見えるため）。

### 5-8. Redmine固有の注意点

- 依存関係を Redmine の `precedes` 関係として書き出すと、**Redmineが自分で後続
  チケットの日付を自動調整する**。本アプリの計画と喧嘩するので、依存は書き出さないか
  `relates` に留めるのが安全。「相手側の自動計算が計画を上書きする」問題は着手前に
  握っておくこと。
- 再計算のたびに全チケットを更新すると**大量の更新通知が飛ぶ**。差分のみpush、
  変更が閾値未満なら無視、pushは明示操作、のいずれかは必要（§3-3の
  スケジュール安定性がここで効く）。
- 担当者は**マッピングを持たない**のが良い。本アプリはチーム単位、Redmineは
  個人単位。チーム＝グループ/カテゴリに対応させる程度に留め、個人アサインは
  Redmine側の自由にする。

### 5-9. 用途を混ぜない

Excel出力には2つの用途が混ざりうる。

- (a) 進捗を書き戻してもらうラウンドトリップ用紙
- (b) 計画の共有・報告帳票

両方に需要があってもシートを分けること。混ぜると (a) の検証が緩む。

### 5-10. 覚悟しておくこと

Excel入出力を入れると「**Excelで計画も編集させろ**」という要求が必ず来る。
それは要件定義で廃止したものそのものなので、断る前提を最初に決めておく。

## 6. 品質

### 6-1. 性能回帰テスト（優先度: 中）

大規模サンプルを使った閾値付きの性能テストが無いと、今回の11倍・85倍の高速化も
次の変更で静かに戻る。CIの実行時間とのバランスを見つつ、少なくとも
「16,000タスクのスケジューリングが N 秒以内」程度は固定したい。

閾値は実行環境によってぶれるため、絶対時間ではなく
「1タスクあたりの処理時間」や「既存サンプルとの比」で見るほうが安定する可能性がある。
