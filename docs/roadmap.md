# 今後の検討事項（設計メモ）

大規模プロジェクトへの対応を検討する中で洗い出した、未着手の課題と設計方針を
記録しておく。実装済みの内容は `docs/architecture.md` を参照。

このメモは「何をやるか」よりも **「なぜその形にするか」「なぜ他の形にしないか」**
を残すことを目的にしている。数値はすべて、同梱の大規模サンプル
（`data/Project_Schedule_Sample_AAA_Large.pschedule`、1,916ジョブ / 16,230タスク）
での実測値。

---

## 1. 現在地

大規模プロジェクトへの対応として、次の4点は対応済み（PR #19 / #20）。

| # | 項目 | 結果 |
|---|---|---|
| 1 | 優先度(Priority)がリソース競合時に反転していた不具合の修正 | 押し出され率が 高優先度0.4% / 低優先度5.8% と正しい順序になった |
| 2 | 締切超過をエラーではなく結果（`Deadline_Overrun_Days`）として返す | 1タスクの超過で全体の日程が得られなくなる状態を解消 |
| 3 | スケジューリングの高速化（`_WorkCalendar` 他） | 16,000タスクで 6.61s → 0.58s |
| 4 | ガントチャートタブのバックグラウンド計算・ジョブ一覧の遅延生成 | タブ切替 18.72s → 0.22s、ファイルを開く 9.74s → 0.72s |

これにより、16,000タスク規模でも一通りの操作が待たされずに行える状態になっている。

加えて、§7の着手順1番目だった **§3-1 依存関係のラグ・種別** を実装済み
（スキーマ v7）。ワークフロー内の依存に `dep_type`（FS/SS）と `lag_days`
（営業日、負ならリード）を持たせ、ASAP・ALAP・平準化の3箇所すべてに反映した。
既定は FS・ラグ0 ＝ 従来と同じ意味なので、既存ファイルは列を足すだけで移行が
完了する。設計と反映箇所は `docs/architecture.md`「依存関係の種別（FS/SS）と
ラグ」を参照。ジョブをまたぐ依存（`job_external_dependencies`）への拡張は
**行わないと決めた**（設定が複雑になりすぎるため。理由は下記 §3-1）。

さらに §7 の2番目、**§4-1 開始固定日（`start_pin_date`）の導入と平準化の
2パス化** も実装済み（スキーマ v9）。当初は `SNET`/`SNLT`/`FNLT`/`START_ON`
の4種別を専用テーブル（`task_constraints`）に持たせる設計だったが、実装後に
**撤回した**——ジョブ数が増えると個別ジョブ単位でのSNET/SNLT/FNLT設定は
現実的に使われなくなり、それをマイルストーン単位で一括設定するテンプレート
機構を検討したものの、概念が複雑になりすぎると判断したため（詳細は下記
§4-1）。最終的に `START_ON`（実績確定・外部都合のピン留め）だけを残し、
`job_task_overrides.start_pin_date` として統合した。ASAP・ALAP・平準化への
反映と、固定タスクを先に予約する2パス構成という設計の骨格は変えていない。
**「固定は入力、日程は出力」の分離も崩していない**——満たせない固定は
データを書き換えて解消せず、`Constraint_Violation` 列として返す。
設計と反映箇所は `docs/architecture.md`「開始固定日と2パス構成」を参照。

## 2. 残っているスケール課題

### 2-1. ジョブ間依存リンクの追加が件数の2乗（優先度: 低）

`ProjectDatabase.add_job_dependency_link()` は1件追加するたびに
`sync_dependency_templates()` を呼び、**その時点の全リンクを走査し直す**。
リンクをN件、1件ずつ張ると、照合回数は 1+2+…+N ≒ N²/2 になる。

全リンクを走査し直すのは、テンプレートの編集・削除やジョブのワークフロー
再割当てのように「どのリンクが影響を受けるか」を絞り込むのが面倒な経路に
対する保険としてこの関数を使っているため。リンク追加の場合は、本来
追加した1件分だけを同期すれば足りる。

**実測（大規模サンプル、既存リンク558件）では体感できる遅さは無い。**

| 操作 | 時間 |
|---|---|
| 同期1回（変更なし。タブ切替のたびに走る） | 0.013秒 |
| リンク1件の追加 | 0.014秒 |
| ダイアログから20件まとめて追加 | 0.28秒 |

実際に踏んだのは、大規模サンプルを**ゼロから558件生成するスクリプト**の
ほうで、`scripts/generate_large_sample.py` では「行を先に挿入してから最後に
1回だけ `sync_dependency_templates()` を呼ぶ」形で回避している。GUI操作で
問題になるのは、既存リンクが数千〜1万件規模になり、そこへ数百件を一度に
足すような場合（1万件なら1件あたり約0.25秒、100件の一括追加で約25秒の見込み）。

**対策案**: リンク追加時は、そのリンク1件分だけを同期する版
（`sync_dependency_templates(link_ids=...)`）を使う。変更は小さい。
リンクがその規模に達する運用が現実になった時点で着手すればよい。

### 2-2. HTMLガントチャートの閲覧性（優先度: 中）

16,230タスクでHTML出力は9.6MB。**出力にかかる時間（約2.2秒）は問題ではない**が、
ブラウザ側で16,000本のバーを描画・操作するのが重い。

**対策案**: 既定をジョブ単位のロールアップ（1ジョブ1バー、期間はタスクの
最早開始〜最遅終了）にして、クリックでタスク単位へドリルダウンする。
チーム別の色分けは、ジョブ内で最も多いチームか、複数チームなら中間色にする等の
整理が要る。

### 2-3. ガントチャートタブの残り2.8秒（優先度: 低）

タブ切替が2.8秒かかる。スケジューリング本体は0.68秒でワーカースレッドに逃がして
あるため、残りはGUIスレッド側の `build_frames()` / `build_display()`（DBの読み出しと
DataFrameの組み立て）と、QGraphicsSceneの構築が占める。

**対策案**: `build_frames()` の結果も `ProjectDatabase.revision` でキャッシュする。
シーン構築は表示中のワークフロー1件分しか作っていないため、これ以上詰めるなら
描画側（ラベルのアイテム数削減など）の話になる。

（対応済み）この2.8秒とは別に、ジョブタブへ寄り道するだけで**スケジューリング
本体（0.68秒）ごと**再実行される不具合があった。`sync_dependency_templates()`
（`gui/db.py`）がタブ切替のたびに実際の変更有無を問わず`db.revision`を
進めていたため、キャッシュ判定が常に不一致になっていた。実際には何も
変わらなかった場合は`db.revision`を進めないよう修正済み（
`docs/architecture.md`「ガントチャートタブのバックグラウンド計算」参照）。

### 2-4. Undoのメモリ（対応不要と判明）

（§8 を実装する場合はこの判断が変わる。確定データをDBに持つとスナップショットが
1.12MBになり、積める操作数が195→56に減る。実測値は §8-5 を参照。）

当初「大規模プロジェクトではUndo段数が黙って減るのでは」と懸念していたが、実測では
スナップショット1件あたり **0.34MB**、上限128MBで **約186操作分**、1操作の記録に
4msだった。ワークフローがテンプレート（ジョブ数に比例しない）であるためDB自体が
小さく収まっており、当面は対応不要。

## 3. エンジン・データモデルの機能不足

### 3-1. 依存関係のラグ・種別（ワークフロー内は対応済み／ジョブ間は行わない）

ワークフロー内の依存（`task_dependencies`）は **FS / SS × ラグ（営業日、負値可）**
に対応済み（§1）。実装して分かった要点を2つ残しておく。

- **ALAP側（`_calc_raw_dates`）への反映が本体。** 前向き（ASAP・平準化）だけに
  ラグを足すのは自明だが、後ろ向きの最遅日程に入れ忘れると、ラグで押し出された
  タスクが「まだ余裕がある」と判定され続け、`distribution_ratio` による配置が
  静かにずれる。SSは「開始同士」の制約なので、終了側の上限へ変換する一手間が要る。
- **ラグは営業日で数える。** 他のすべての計算が営業日ベースである以上、ここだけ
  暦日にすると「2日空ける」の意味が週末をまたぐかどうかで変わる。

#### ジョブをまたぐ依存には広げない（撤回）

ジョブをまたぐ依存（`job_external_dependencies`）は FS・ラグ0 のまま据え置く。
当初は「残り」として記録していたが、**設定が複雑になりすぎる**ため行わないと決めた。

ジョブ間の依存は、依存テンプレート（ワークフローペア単位）→ ジョブ間リンク →
個別のタスク依存、と3層で自動展開される。ここにラグを入れると、

- ラグをどの層に持たせるか（テンプレートの既定値か、リンクごとか、個別行か）
- 既定値と個別の上書きのどちらが効いているのか
- 再同期（`sync_dependency_templates()`）で個別の上書きを消さない仕組み

を決めることになり、設定する側から見て「このラグはどこで決まったのか」が
追えなくなる。ジョブ数が増えると個別ジョブ単位の設定が使われなくなる、という
§4-1（SNET/SNLT/FNLT の撤回）と同じ構図でもある。

ジョブ間で間隔が必要な場合は、既存の仕組みで代用する——後続タスクの
開始固定日（`start_pin_date`）や所要日数の上書き、あるいはワークフローに
待ちのタスクを入れる。

### 3-2. 祝日を稼働日に戻せない（優先度: 低／実装コスト: 小）

必要になったら着手する（祝日出勤の運用が実際に出てきた時点）。

`_WorkCalendar` は日本の祝日を無条件に休業日として扱い、`holidays` テーブルは
休業日の**追加**しかできない。以下が表現できない。

- 祝日出勤（繁忙期の休日稼働）
- 法改正による祝日の移動（五輪年の移動祝日のような例外）

**対策案**: `holidays` に `is_working_day INTEGER NOT NULL DEFAULT 0`（1なら
「例外的に稼働する日」）を足し、`_WorkCalendar` の構築時に祝日マスクより後に
適用する。

### 3-3. スケジュールの安定性（優先度: 中／外部連携の前提）

`_job_ratio_jitter()` はジョブIDのハッシュで分散量を決めているため、内部IDが
変われば日程が動く。また、入力を少し変えるだけでスケジュール全体が
入れ替わりうる（グリーディな1パス方式なので当然ではある）。

これは単体では実害が小さいが、**外部タスク管理システムと同期し始めると効いてくる**。
小さな編集で数千タスクの日程が総入れ替えになると、外部システムとの差分が
意味を持たなくなり、更新通知も大量に飛ぶ。

**対策案**: 「前回の結果を初期解として尊重する」モードを設ける。前回配置と
同じ日程が取れるならそこを優先し、取れない場合だけ動かす。§4-1の
`start_pin_date` があれば、前回結果を開始固定日として与える形でも近い
ことができる。

### 3-4. タスクの分割・中断（優先度: 低／明文化のみで可）

現在のモデルでは、タスクは**連続した営業日ブロックを1ラインで占有**し、
中断・分割・プリエンプションを表現できない。実績を取り込むと「着手したが
止まっている」状態は必ず出る。

無理に対応する必要はないが、**モデルの制約として明文化しておくべき**
（実績反映の設計時に必ず論点になる）。

## 4. 「試す」ための仕組み

「このタスクを前倒ししたらどうなるか」「このタスクはもっと後ろでもいいのでは」
を試せるようにする。

### 4-1. 開始固定日（`start_pin_date`）の導入（実装済み・当初案から縮小）

**実装済み**（§1）。ただし**当初の設計（`SNET`/`SNLT`/`FNLT`/`START_ON` の
4種別を持つ `task_constraints` テーブル）は実装後に撤回し、`START_ON` だけを
`job_task_overrides.start_pin_date` として残す形に縮小した。** 経緯と、
実装して確かめられたことを書いておく。

#### なぜ縮小したか

`SNET`/`SNLT`/`FNLT` は個別ジョブ単位で設定する前提だったが、**ジョブ数が
増えると個別設定が現実的でなくなる**という指摘があった（数百ジョブの1つ1つに
日付を入れて回る運用は成立しない）。対策として「マイルストーン×ワークフロー×
タスク単位で一括設定し、そのマイルストーンを実効的に使っている全ジョブに
自動適用するテンプレート」を検討した。

設計としては筋が良かった。既存の`workflow_dependency_templates`（ワークフロー
ペア単位のテンプレート→ジョブ間依存への自動展開）とほぼ同じ形で、しかも
**「展開して保存」ではなく「都度解決」で作れる**——`_parse_tasks()`が既に
ジョブのタスクごとに実効マイルストーンを1件確定させているので、そこに
テンプレート検索を足すだけで済み、`sync_dependency_templates()`のような
再同期関数も、それを呼ぶ変更経路の洗い出しも一切不要になる。「ジョブの
マイルストーンが変わると追従できるか」という当初の懸念は、都度解決なら
原理的に発生しない。

**それでも撤回した。** テンプレート×実効マイルストーンの解決×個別上書きとの
優先順位、という概念の総量が、得られる価値（数種類の制約を数百ジョブに一括で
配れること）に見合わないと判断したため。個別ジョブ単位の`SNET`/`SNLT`/`FNLT`
自体も、テンプレート機構が無ければ結局「設定されないまま使われない機能」に
なる。**`START_ON`（実績確定・外部都合のピン留め）だけは事情が違う**——
これは元々1ジョブ1タスクに閉じた意味を持ち、ジョブ数が増えても「一括設定」を
必要としない（実績はジョブごとに個別に確定するものだから）。そのため
`START_ON`だけを残し、他の3種別と専用テーブルは撤去した。

#### 実装して確かめられたこと

- **2パス構成の効果は実測で確認できた。** ライン数1のチームで、優先度の低い
  ジョブのタスクを先頭に固定すると、優先度の高いジョブがそのぶん後ろへ押し出される
  （1パスのままだと固定タスクの番が来たときにラインが埋まっていて置けない）。
  この挙動はテストで固定してある。
- **「固定は入力、日程は出力」を守ると、整合性維持コードが本当に増えない。**
  依存関係やライン数と矛盾する固定もそのまま保存でき、スケジューリング実行時に
  診断結果として出てくるだけで済んだ。マイルストーン整合ロジック
  （`cascade_milestone_to_successors` 等）に相当するものは1つも要らなかった。
- **`START_ON`を`job_task_overrides`に統合したことで、テーブルが1つ減った。**
  `override_days`等と性質が同じ（このジョブのこのタスクだけ既定と違う）
  「差分のみ保持」の1列として扱えるため、専用テーブル・専用CRUD・専用の
  編集ダイアログが丸ごと不要になった。GUIは`DefaultAwareSpinBox`と同じ発想の
  1列ウィジェット（`OptionalDateEdit`）だけで足りている。
- **§5の再計画（実績反映）が`START_ON`だけで組めることをシミュレーションで
  確認した。** 完了タスクは`START_ON`＋`override_days`（実績の所要日数で
  上書き）で固定、進行中タスクは`actual_start`＋「as_ofから残り日数ぶん」の
  `override_days`で固定、未着手タスクには`as_of_date`をその回のプロジェクト
  開始日として渡す——という3つの組み合わせで、依存する後続タスクも実際の
  終了日を自動的に見て正しく再配置された。唯一の注意点は、固定タスクの予約が
  過去日（as_ofより前）の分もそのまま「使用量」に計上されること。未来の
  タスクの配置には影響しないが、複数の過去の固定が重なってライン数を超えると
  `Constraint_Violation`に載る——事実として間違ってはいないが、§5本体を
  実装する際は「もう変えようがない過去」への警告をノイズにしない工夫
  （as_ofより前の超過は表示を落とす等）を検討したほうがよい。
- **残りは §4-2 のシナリオ比較。** `START_ON`をベースラインに直接持つ
  「段階1」相当まで到達したので、次は `scenarios` テーブル（段階2）か、
  その前に段階0の「その場で再計算して名前を付けて比べる」か、という選択になる。

### 4-2. シナリオ（案）の比較（優先度: 中）

「前倒ししたらどうなるか」で本当に欲しいのは、①ベースラインを保ったまま
②差分を当てた別案を計算し ③**並べて差分を見る**、という流れ。段階を踏む。

- **段階0（実装ほぼゼロ）**: ガントチャートタブで `distribution_ratio` 等をその場で
  変えて再計算し、結果に名前を付けて保持して次の結果と比較する。これだけで
  「試す」体験の大半が得られる。
- **段階1**: `start_pin_date` をベースラインに直接導入する（シナリオ無し）。
  実装済み（§4-1）。
- **段階2**: `scenarios` テーブルを入れ、固定日とパラメータ上書きを紐付ける。

`job_task_overrides` が既に「差分のみ保持」という思想で作られているので、
その考え方を素直に拡張できる。**シナリオを持つ意味は比較にある**ので、
`result_df` 同士を `Job:Task` キーで結合した差分表示（何日動いたか、締切超過が
増減したか、チーム別の負荷ピークがどう変わったか）を必ずセットで作ること。
`gui/resource_histogram.py` の描画部分（`build_histogram_scene`等）は
プロジェクト分析タブへの機能移管に伴い廃止済み。汎用の階段関数区間化
（`compute_step_segments`）だけが残っているので、描画自体は改めて作る必要がある。

## 5. 進捗の外部連携

計画を外部のタスク管理システム（Redmine等）へ書き出し、実績を取り込んで
「当初計画とのズレ」「現状からの再計画」を見られるようにする。

> **実装済みの軽量版との関係**: `job_task_overrides.status`（タブ3「タスク上書き」の
> 「状態」列。未着手／進行中／完了）は、プロジェクト分析タブの「タスクの状態」KPI
> のために先行して追加した手動記録欄。Excel入出力・`progress_snapshots`・
> 再計画ルール等（この節の本体）は依然として未着手の将来課題だが、別物では
> なく**この`status`列を土台にする**——5-3の「進捗入力」シートの状態列は
> ここに書き戻す想定（現状は未着手／進行中／完了の3区分のみのため、
> 「中止」を含めるならこの列自体の拡張が要る）。

### 5-1. 基本方針: 計画と進捗記録のツールを分ける

本アプリが日々の実績入力まで抱えると、毎日使われるツールになりUI要求が跳ね上がる
（通知・権限・コメント・添付…）。本アプリは **「計画と再計画のエンジン」** に
集中し、進捗の記録は外部に任せるのが良い。

### 5-2. 最初はファイル（Excel）で作る。API直結を先に作らない

理由:

- Redmine以外（Jira / Backlog / スプレッドシート）へも展開できる
- **「サーバー不要・ローカル完結」という非機能要件を壊さない**
  （`.pschedule` にAPIキーを保存する、という面倒を先送りできる）
- テストが書ける

```
Redmine API ─┐
Excel ───────┼→ 中間形式（進捗レコード）→ progress_snapshots → 再計画
CSV/JSON ────┘
```

**Excelを選ぶ積極的な理由**: データ検証（ドロップダウン）・条件付き書式・
シート保護が使えるため、「壊れた入力」を構造的に減らせる。CSVには無い武器で、
本アプリの非機能要件「ミスの構造的防止」と同じ思想。旧Excel入力の廃止に伴い
`openpyxl`依存も削除済みのため、この案に着手する際は再度依存に加える必要がある。

**旧Excel（廃止済み）とは別物**であることに注意（`docs/requirements.md` の
「対象外」も参照）。

| | 旧Excel（廃止した） | 新Excel（この案） |
|---|---|---|
| 目的 | 計画の入力（マスタデータ） | 進捗の交換（実績） |
| 構造 | 8シートがID（`WF_CHAR`、`JOB:TASK`）で相互参照 | 1行1タスクのフラットな表 |
| 人が触る所 | 全部（依存関係・チーム・日数・ID） | 状態・実績日・残日数だけ |

廃止理由（IDのタイプミス、参照ミス、依存関係の全体像が掴めない）は、進捗交換には
1つも当てはまらない。

### 5-3. シート構成案

- **`進捗入力`** — 1行1タスク
  - 隠し＋保護: `Key`（`JOB_003:T_012` 相当の安定キー）
  - 参照用（読み取り専用・**書き戻さない**）: ジョブ名 / タスク名 / チーム /
    マイルストーン / 計画開始日 / 計画終了日 / 計画日数
  - 入力列（**書き戻す**）: 状態（未着手・進行中・完了・中止）/ 実績開始日 /
    実績終了日 / **残日数** / 備考
- **`メタ`** — `as_of_date` / 書き出し日時 / スキーマバージョン / 書き出し元のハッシュ
- **`凡例`** — 入力ルール

### 5-4. 取り込み時の検証

必ず **プレビュー → 確認 → 適用**（Undo 1単位）とする。

- スキーマバージョン照合、書き出し元ハッシュで「どの書き出しに対する回答か」を照合
- **キーが無い／不明な行は黙って無視せず、一覧で提示する**
- 状態と日付の整合（完了なのに実績終了日が空、`as_of_date` より未来の実績日 等）

### 5-5. 必ず踏む3つの論点（Redmineでも形を変えて出る）

1. **同一性の維持** — Excelは行が並べ替えられ、コピペされ、挿入・削除される。
   **名前でのマッチングは絶対にやらない。** 隠し列の安定キーだけで突き合わせる。
   一度書き出したタスクの内部IDは再利用・再生成しない（＝削除ではなく無効化を
   徹底する。`is_active` の思想は既にある）。
2. **正／従の線引き** — 最初に決めないと必ず破綻する。**片方向push（計画）＋
   片方向pull（実績）に割り切る。**

   | 項目 | 正 |
   |---|---|
   | タスクの存在・構造・依存関係 | **本アプリ** |
   | 見積日数・担当チーム・優先度 | **本アプリ** |
   | 計画開始日／終了日 | **本アプリ**（シミュレーション結果） |
   | 実績開始日・実績終了日・状態・残作業 | **外部システム** |

   双方向で同じフィールドを編集可能にすると、コンフリクト解決を作る羽目になり
   コストが跳ね上がる。「外部で計画日を動かしても取り込まない（ただし"計画と
   違う"という差分としては見える）」が正しい割り切り。

   **ここを曖昧にすると「Excelで日数を直したのに反映されない」というクレームに
   なり、結局双方向同期を作る羽目になる。** 計画列はシート保護と凡例で
   「編集しても反映しない」ことを明示する。
3. **粒度（1:1を前提にしない）** — 「1タスクを3人で分担 → 外部では3チケット」は
   普通に起きる。`external_links` は `local_id : external_id` が 1:N を許す形に
   しておく。取り込み時は「子が全部閉じたらタスク完了、残日数は合計」という
   集約ルールを持つ。最初から1:1前提のスキーマにすると必ず作り直しになる。

   逆に「外部にあるが本アプリに無い」突発作業も必ず発生する。これを
   取り込めるようにしておくと価値が高い（＝計画外作業がチームのキャパシティを
   食っている、という可視化になる）。

### 5-6. 保持すべきデータ

**最重要は `as_of_date`（基準日）。** これが無いと実績データは何の意味も持たない。
全ての実績スナップショット・全ての計算結果に必須。

```sql
CREATE TABLE progress_snapshots (       -- 取り込んだ実績（時系列で残す）
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    as_of_date TEXT NOT NULL, source TEXT NOT NULL, imported_at TEXT NOT NULL
);
CREATE TABLE progress_task_status (
    snapshot_id INTEGER NOT NULL REFERENCES progress_snapshots(id) ON DELETE CASCADE,
    job_id INTEGER NOT NULL, workflow_task_id INTEGER NOT NULL,
    status TEXT NOT NULL,               -- not_started | in_progress | done | cancelled
    actual_start TEXT, actual_finish TEXT,
    remaining_days REAL,                -- ★ 進捗率より圧倒的に重要
    percent_done REAL, spent_hours REAL, note TEXT
);

CREATE TABLE schedule_runs (            -- 計算結果のスナップショット
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    label TEXT, scenario_id INTEGER, as_of_date TEXT,
    computed_at TEXT NOT NULL, params_json TEXT NOT NULL,
    is_baseline INTEGER NOT NULL DEFAULT 0
);
CREATE TABLE schedule_run_tasks (
    run_id INTEGER NOT NULL REFERENCES schedule_runs(id) ON DELETE CASCADE,
    job_id INTEGER, workflow_task_id INTEGER,
    start_date TEXT, end_date TEXT, team_id INTEGER,
    milestone_id INTEGER, resource_adjusted INTEGER, overrun_days INTEGER
);

CREATE TABLE external_links (           -- 外部システムとの対応（1:N可）
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    local_kind TEXT NOT NULL,           -- 'job' | 'job_task'
    job_id INTEGER, workflow_task_id INTEGER,
    system TEXT NOT NULL,               -- 'redmine' | 'excel' 等
    external_id TEXT NOT NULL, external_url TEXT,
    status TEXT NOT NULL DEFAULT 'active',  -- active | missing | detached
    last_synced_at TEXT, last_pushed_hash TEXT
);
```

**`remaining_days`（残り所要日数）を第一級で持つこと**を強く勧める。
「80%完了」は残り2割を意味しない。`done_ratio` しか取れない場合は
`remaining = ceil(days × (1 - ratio))` で近似しつつ、**手で上書きできる**ように
しておく。実務ではここが一番効く。

**その他、後で効くもの**

- **休業日カレンダーの実体化** — 現在は日本の祝日をコード内の近似式で計算して
  いる（`_vernal_equinox_day` 等）。実績と突き合わせる際、「その日は稼働日
  だったか」の判定が過去に遡って一貫している必要がある。計算に使った休業日集合を
  `schedule_runs` に保存するか、祝日をテーブルとして実体化する。
- **見積の履歴** — `default_days` をいつ何から何に変えたか。実績と突き合わせると
  見積バイアスが定量化できる。
- **チームの実効キャパシティ** — `team_capacity_changes` は計画値。実績から
  「実際は何本並行していたか」を逆算してヒストグラムに重ねると、計画前提の
  妥当性が検証できる。

### 5-7. 再計画のルール

> **この節は §8 で置き換えた。** ベースラインは `schedule_runs` ではなく
> `confirmed_schedule`（確定）として持ち、基準日は `project.replan_base_date` に
> 内部保持する。下記の「完了／進行中／未着手の3分類で固定する」という骨格は
> §8 でもそのまま使っている。

**ベースライン（当初計画）の保存が必須。** 「ズレの確認」とは
「実績 vs 現計画 vs ベースライン」の3系列比較だから。

再計画時のスケジューラ側の扱い（§4-1の2パス構成とまったく同じ形）:

- **完了タスク**: 実績日で固定。後続の下限は実績終了日
- **進行中タスク**: `actual_start` で固定、終了 = `as_of + remaining_days`（営業日換算）
- **未着手タスク**: `as_of_date` を新しい下限として通常どおり平準化
- **リソースの二重計上を避ける**: 進行中タスクは `as_of` 以降の残り期間だけ
  ラインを消費する（予約テーブルを `as_of` 以降で持つ）
- **締切超過はエラーにせず結果として返す** — 実績を入れれば締切に間に合わないのが
  普通なので、この点は §1 の2で先に手当て済み

3系列が揃うと、SPI相当の指標と **マイルストーン・トレンド・チャート**
（各 run の `as_of` を横軸、各マイルストーンの予測着地日を縦軸にプロット）が
出せる。実装は既存データをプロットするだけだが、**この種のツールで最も費用対効果の
高い可視化**だと考えている（「締切が守れそうか」ではなく「守れなくなりつつあるか」
が見えるため）。

### 5-8. Redmine固有の注意点

- 依存関係を Redmine の `precedes` 関係として書き出すと、**Redmineが自分で後続
  チケットの日付を自動調整する**。本アプリの計画と喧嘩するので、依存は書き出さないか
  `relates` に留めるのが安全。「相手側の自動計算が計画を上書きする」問題は着手前に
  握っておくこと。
- 再計算のたびに全チケットを更新すると**大量の更新通知が飛ぶ**。差分のみpush、
  変更が閾値未満なら無視、pushは明示操作、のいずれかは必要（§3-3の
  スケジュール安定性がここで効く）。
- 担当者は**マッピングを持たない**のが良い。本アプリはチーム単位、Redmineは
  個人単位。チーム＝グループ/カテゴリに対応させる程度に留め、個人アサインは
  Redmine側の自由にする。

### 5-9. 用途を混ぜない

Excel出力には2つの用途が混ざりうる。

- (a) 進捗を書き戻してもらうラウンドトリップ用紙
- (b) 計画の共有・報告帳票

両方に需要があってもシートを分けること。混ぜると (a) の検証が緩む。

### 5-10. 覚悟しておくこと

Excel入出力を入れると「**Excelで計画も編集させろ**」という要求が必ず来る。
それは要件定義で廃止したものそのものなので、断る前提を最初に決めておく。

## 8. 計画の確定と再計画（合意形成サイクル）

想定している運用は次のサイクルになる。

1. プロジェクト初期に期間・ワークフロー・ジョブを作り、シミュレーションを
   繰り返して組織内で合意する
2. その計画で仕事に着手し、週次ミーティングで着手・完了を反映する
3. マイルストーンや月次で振り返り、必要なら再シミュレーションして再合意する
4. 2〜3を繰り返す

この節は、そのサイクルを回すために必要な仕組みの設計をまとめる。
**既存の §5-6/§5-7（`schedule_runs` によるベースライン保存と再計画）を
置き換える。** §5 の残り（Excel入出力・`progress_snapshots`・外部連携）は
そのまま有効で、この節の上に乗る。

### 8-1. 何を解決するのか

懸念は「合意したスケジュールが、あとから変わってしまう」こと。ただし、
これは性質の違う3つが混ざっている。分けないと対策も混ざる。

| | 内容 | 現状 |
|---|---|---|
| (a) 決定論性 | 同じ入力なら同じ結果か | **満たされている。** スケジューラは `today()` / `now()` を一切参照していない（`project_scheduler.py`・`gui/gantt_generator.py`・`gui/summary_metrics.py`）。保存して閉じ、翌週開いても日程は変わらない |
| (b) 入力変化への安定性 | 入力を少し変えたときの揺れ | **崩れる。** グリーディな1パスなので、ジョブを1件足しただけで数千タスクの配置が入れ替わりうる（§3-3） |
| (c) アプリのバージョン差 | 算出ロジックを変えたとき | **崩れる。** `_job_ratio_jitter()` の定数やアルゴリズムを変えれば、入力が1バイトも変わらなくても合意済みの日程が動く |

**(c) が設計を決める。** 合意した日程は「再計算で再現するもの」であってはならず、
**保存されたデータ**でなければならない。安定化（(b) への対策）をいくら積んでも
(c) は防げない。したがって、合意した時点で日程を明示的に固定して持つ。

固定するとシミュレーションの自由度は失われるが、**進行中に計画が変わるリスクの
ほうが問題**という判断で、固定を優先する。失われる分は 8-6 の「確定を無視して
計算」で埋め合わせる。

なお (b) に効く小さな地雷として、jitter のキーが `Job_ID` =
`"JOB_<AUTOINCREMENT>"`（`gui/gantt_generator.py`）＝内部IDの文字列である点がある。
ジョブを削除して作り直すと、そのジョブだけでなくリソース競合の連鎖で無関係な
ジョブの日程まで動く。`jobs` に作成時のUUID列を足してキーを移すのが、変更量の
わりに効果が大きい。

### 8-2. 確定（`confirmed_schedule`）

合意時に、その時点の計算結果を全タスク分保存する。

```sql
CREATE TABLE confirmed_schedule (
    job_id           INTEGER NOT NULL REFERENCES jobs(id) ON DELETE CASCADE,
    workflow_task_id INTEGER NOT NULL REFERENCES workflow_tasks(id) ON DELETE CASCADE,
    start_date TEXT NOT NULL,
    end_date   TEXT NOT NULL,
    days       INTEGER NOT NULL,
    team_id    INTEGER REFERENCES teams(id) ON DELETE SET NULL,
    PRIMARY KEY (job_id, workflow_task_id)
);
```

スケジューラから見れば、確定行は開始固定日と同じ「動かせない入力」であり、
パス1で先に予約する（§4-1 の2パス構成がそのまま使える）。解決順は

> **手動ピン（`start_pin_date`） > 確定（`confirmed_schedule`） > 自由**

手動ピンを優先するのは、それが**より新しい意図的な操作**だから（確定後に
ガントでバーを動かしたら、その位置になってほしい）。

**手動ピンと同じ列に入れない。** `start_pin_date` は「このタスクはこの日から」
という汎用の固定であり、今後ガントチャート上でのタスク編集の書き込み先になる。
確定を同じ列に流し込むと、
- ユーザーが意図して打ったピンと、一括確定で付いたピンが区別できなくなる
- **すべてのバーが固定表示になり、「どれを自分で動かしたか」がガント上で
  見分けられなくなる**——ピンは希少であることに価値がある

`pin_origin` のような1列の区分値で分ける案もあるが、**列を分けるほうが安全**。
1列だと確定操作が手動ピンの出自を上書きし、確定解除でユーザーの手動ピンまで
消える経路ができる。テーブルが別なら、この事故が構造的に起こらない
（確定解除は `DELETE FROM confirmed_schedule` だけで済む）。

**`days` と `team_id` を確定行が持つ理由。** これが無いと、確定行は外部キー経由で
`workflow_tasks` を見にいくため、**あとからワークフローの所要日数やチームを直すと、
終わった仕事の実績が遡って書き換わる**。振り返りで見ている数字（チーム別の実績
負荷、実際にかかった日数）が、ワークフローを直した瞬間に変わってしまう。
マイルストーンは逆に遡って変わってよい（締切が動いたなら、過去の実績が新しい
締切に対して超過していた、と見えるのが正しい）。

**`.pschedule` の外（別ファイル）に置く案は採らない。** Undoスナップショットが
DB全体のバイト列（`ProjectDatabase.serialize_state()`）である以上、DB内に置くと
必ずUndoのメモリに乗る——これを避けるには外に出すしかない、という技術的理由から
一度は別ファイル案を検討した。しかし運用上の管理が煩雑になり、「確定 vs 現在の
計算結果」の比較もファイルをまたぐことになる。実測したUndoへの影響（8-5）が
許容範囲だったため、DB内に持つ。

**確定は1世代だけ持つ。** 合意履歴を何世代もDBに溜めると、Undoスナップショットが
比例して重くなる。履歴が必要になったら、確定時にCSVを併せて書き出す形で足す。

### 8-3. 基準日は内部にだけ持つ

再計画では「指定した日より前にタスクが再配置されてはならない」が要る。
`project_start_ord` は ASAP計算と平準化パス2の下限として使われているので、
そこへ再計画日を渡せばよい。パス1（固定タスクの予約）は下限を見ずに無条件で
予約するため、**完了済みタスクは過去に置いたままにできる**。カレンダーの範囲
計算も「開始固定日はプロジェクト開始日より前にも置きうる」として既に
`pin_ords` を含めているので、過去にピンがある状態は設計上すでに想定済み。

**`project.start_date` を進めてはいけない。** 基本情報設定タブの「開発開始日」
入力そのものが変わり、プロジェクト全体の期間の意味が壊れ、マイルストーンとの
整合も取れなくなる。加えてこの日付は**チームの稼働本数変更の起点**としても
使われている（`gui/tab_basic_info.py`）ので、稼働本数の時系列の見え方まで変わる。

代わりに `project` へ内部専用の基準日（仮に `replan_base_date`）を1つ持ち、
**確定行を持たないタスクの下限**として常に使う。基本情報タブには出さない。
画面に出るのは、再計画した後の状態帯（「9/28 から新計画（9/24 再計画）」、8-7）と
再計画ダイアログの入力欄だけ。ユーザーにとって基準日は実質「新しい計画が始まる日」
なので、その言い方で見せる。

基準日は**未来の日付でもよい**（「今週は今の計画のまま走らせ、来週月曜から新計画」
のような運用）。その場合の未着手タスクの扱いは 8-6 の「再計画する」を参照。

**再計画時だけの一時パラメータでは足りない。** 確定後にワークフローへタスクを
追加すると、そのタスクは全ジョブに未確定タスクとして現れ、下限が当初の
`project.start_date`＝過去になって**過去に配置される**。「基準日より前に
置かれない」は再計画の瞬間だけでなく継続的に必要なので、保存する。

スケジューラへ渡す経路は `build_frames()` が組み立てる `df_project` の
`Start_Date` 列1セルなので、そこを差し替えるだけでよい。

### 8-4. ワークフローの変更との整合

合意後もジョブ追加・ワークフロー変更・タスクの実行有無は常に起こる。
これらを既存の確定に破綻なく統合する必要がある。

#### タスクの削除 → 「廃止」に変える

実施済み（進行中・完了）の記録があるタスクをワークフローから削除すると、
`ON DELETE CASCADE` で確定行も `job_task_overrides` の行も消える。
**合意した日程と実施した事実が黙って消える経路**になる。

対策は「本当に消さず、情報を持ったまま整合を取る」。`workflow_tasks` に
真偽値を1つ足す。

```sql
ALTER TABLE workflow_tasks ADD COLUMN is_retired INTEGER NOT NULL DEFAULT 0;
```

- 実施済みの記録が**無ければ** → 従来どおり本当に削除する（既存の依存の
  橋渡しがそのまま働く）
- 実施済みの記録が**有れば** → `is_retired = 1` にする（削除しない）

実効的な有効/無効は、`build_frames()` が `Is_Active` 列を作るときに解決する。

```
is_retired = 1 のとき
    status が 進行中 / 完了 → 有効（実施した事実なので残す）
    それ以外                → 無効
is_retired = 0 のとき
    job_task_overrides に行がある → その is_active に従う
    行が無い                       → 有効
```

**`is_active` は書き換えない。** 廃止時に「未着手だから」と `is_active = 0` を
書き込む案を検討したが、**ユーザーが以前から意図して無効にしていたタスクと
区別がつかなくなり、廃止を解除したときにどちらを復活させるべきか判定できない**。
廃止中は `is_active` を読まないことで、この問題自体が消える。

この形の利点は3つ。

- 廃止／解除が1行の真偽値トグルになる（一括書き込みも後始末も不要な、完全に
  対称な操作）
- `job_task_overrides` の行が増えない
- **スケジューラは廃止を知らなくてよい。** 解決は `build_frames()` だけで、
  `project_scheduler.py` は無変更。無効タスクをまたぐ依存の橋渡しがそのまま効く

`is_retired` のタスクは新規ジョブには最初から入らない（新規ジョブは
`job_task_overrides` に行を持たないため、既定で無効になる）。ノードキャンバス
では灰色＋「廃止」表示にする。

当初は「ワークフローのタスクは削除し、確定行のほうを切り離して履歴として残す」
案（確定行の `workflow_task_id` を NULL にし、タスク名・チーム名をスナップ
ショット列に退避する）を検討したが、**NULL許容の外部キー、非正規化列、
「ワークフロー外の履歴行」をガントとタブ3にどう出すかという新しいGUI課題が
まとめて発生する**ため撤回した。廃止方式ならいずれも要らない。

#### タスクの追加・依存の組み替え → 不変条件の検査で拾う

「追加されたタスクが実行不可のジョブ（後工程まで終了している）では無効にする」
という判定は、**タスク追加の瞬間にはできない**。ノードキャンバスでは「タスクを
追加する」と「依存を繋ぐ」が別操作なので、追加直後の新タスクは後続を1つも
持っておらず、判定材料が存在しない。

そこで一度きりの判定ではなく、不変条件の検査にする。

> **未着手なのに、後続タスクが実施済み（進行中／完了）である** → そのジョブでは実行不可

ワークフロー編集の後に走らせ、「N件のジョブでこのタスクは実行できません
（後工程が既に完了）。無効にしますか？」と出す。この1つの検査で、タスクの追加・
依存の繋ぎ替え・廃止の取り消しの3つを同時に拾える。判定を操作ごとに散らさずに済む。

ここで書き込む `is_active = 0` は `is_retired = 0` のタスクに対する明示操作なので、
廃止解除で勝手に復活しない（＝正しい）。

#### 依存の組み替えに抜けは無い

確定後は全タスクが固定されているため、`_check_constraint_violations()` の
検査対象になる。

| 組み替え | 何が起きるか |
|---|---|
| A→B を B→A に逆転（Aが完了、Bが未着手） | A は固定、B は基準日以降。A の着手可能日が B の完了後になり、**A の `Constraint_Violation` として出る** |
| 実施済みタスクへ新しい依存を足す | 同上。固定側で検出される |
| 完了タスク → 未着手タスク の依存を削除 | 影響なし。完了タスクの終了日は基準日以前なので、後続の下限（基準日以上）を変えない |
| 実施済み同士の依存を変更 | 両方固定なので日程は動かない。矛盾があれば違反として出る |
| 循環になる組み替え | 既存の `CircularDependencyError`。廃止タスクだけで閉じた循環を打ち切る既存仕様もそのまま効く |

**「依存の両端のうち少なくとも一方が固定なら検査される。両方とも未確定なら、
両方が自由に動けるので矛盾しようがない」**——これで場合分けが尽きている。
全タスクを確定させたことが、ここで効いている。

### 8-5. 実測

大規模サンプル（`data/Project_Schedule_Sample_AAA_Large.pschedule`、
1,916ジョブ / 16,230タスク）での実測値。

#### Undoのメモリ

`confirmed_schedule` に全タスク分（16,230行）を入れたときのDBサイズと、
`UndoManager` の上限128MBで積める操作数。

| | DBサイズ | Undo上限128MBで |
|---|---|---|
| 現状 | 0.34 MB | 195操作 |
| 確定テーブル（8-2 の形） | 1.12 MB | **56操作** |
| （不採用）切り離し用にタスク名・チーム名を常時保存 | 1.80 MB | 35操作 |

56操作あれば実用上問題ない。§2-4 で「Undoのメモリは対応不要」と判断した前提が
変わるので、確定を入れる際はこの数値を再確認すること。**確定を複数世代持たせると
比例して減る**（8-2 で1世代に限る理由）。

#### 廃止タスクが多数ある状態でのスケジューリング性能

`is_retired` の効果と等価な状態（`job_task_overrides.is_active = 0` の行を
大量に作る）で計測。鎖の途中に**連続した**穴を空ける、橋渡しが再帰的に解決
される最悪ケース。

| 廃止率 | 無効化行 | `build_frames` | スケジューリング | 有効タスク | 1件あたり |
|---|---|---|---|---|---|
| 0% | 0 | 0.014s | 0.759s | 16,230 | 46.8µs |
| 10% | 766 | 0.017s | 0.752s | 15,464 | 48.6µs |
| 25% | 2,902 | 0.024s | 0.661s | 13,328 | 49.6µs |
| 50% | 7,500 | 0.053s | 0.506s | 8,730 | 57.9µs |
| 80% | 11,978 | 0.069s | 0.352s | 4,252 | 82.7µs |

橋渡しを含む `_parse_tasks()` だけを切り出すと、廃止件数にほぼ依存せず
**一定**（0.17〜0.22秒）だった。連続した穴を12,000件作っても増えない。

結論として**性能上の懸念は無い**。総時間は廃止を増やすほど短くなり
（0.76s → 0.35s）、絶対時間がベースラインを超えることは一度もない。
1タスクあたりの単価は最悪ケースで +77% になるが、これは分母（有効タスク）が
減るためで、実時間は下がっている。なお `build_frames` の増加（0.014s → 0.069s）は
無効化行をDBから読むぶんであり、**8-4 の設計では廃止時に行を書かないので
実装後には発生しない**（上の数値は悲観側に振れている）。

### 8-6. 操作

ユーザーに見せる操作は3つに絞る。いずれも `db.undo_group()` で1 Undo単位。

| 操作 | 中身 |
|---|---|
| **確定する** | 現在の計算結果を全タスク分 `confirmed_schedule` へ書き込む |
| **再計画する** | 基準日 D を指定 → 完了・進行中（`status`）の確定行は残し、未着手の確定行のうち**残すもの以外**（下記）を削除 → `replan_base_date` を D にして1回計算 → 結果を未着手タスクの確定行として書き戻す |
| **確定を解除する** | `confirmed_schedule` を全削除（手動ピンは残る） |

#### 確定を書き込むのは、この2操作だけ

> **不変条件: スケジューリングの実行そのものは `confirmed_schedule` に一切
> 書き込まない。書き込むのは「確定する」「再計画する」という明示操作だけ。**

ガントチャートタブ・プロジェクト分析タブの自動再計算（`gui/schedule_cache.py` の
`ensure_fresh()`）は、計算して表示するだけでDBには触れない。ジョブやワークフローの
編集も確定行を作らない。したがって、

- **一度も「確定する」を押していないファイルでは `confirmed_schedule` は空のまま**で、
  日程は開くたび・編集するたびに自由に計算される（＝従来どおりのシミュレーション）
- そのとき固定されるのは、ユーザーが自分で打った手動ピン（`start_pin_date`）だけ

これは §4-1 の「**固定は入力、日程は出力**」の言い換えでもある。確定とは、
計算結果をユーザーが明示的に入力へ昇格させる操作であり、**計算結果が黙って入力へ
回り込む経路を作ってはならない**。操作のたびに確定が溜まっていく作りにすると、
この分離が崩れて「いつの間にか何も動かなくなっている」状態になる。

実装上の注意として、確定を書き込むと `db.revision` が進むため `schedule_cache` が
1回再計算する。**このとき出る日程は、書き込んだ確定とタスク単位で一致するはず**
（確定行がそのままパス1のピンとして再現されるため）。一致しなければ確定の
書き込み内容か 8-2 の解決順に誤りがある、という自己検査になるので、テストで
固定しておくとよい。

再計画の区分に `status`（`job_task_overrides.status`、未着手／進行中／完了）を
そのまま使うので、**新しい区分軸を足さずに済む**。実績日（`actual_start` /
`actual_finish` / `remaining_days`）の入力欄は持たず、計画日で代用する——
ズレが大きいタスクだけ、ガント上でバーを動かして手で直す（＝`start_pin_date`）。
足りないと分かってから §5-6 の形で足せばよい。

再計画時、**基準日より前に手動ピンがある未着手タスク**は確認メッセージを出す。

#### 基準日が未来のとき・過去のとき

再計画を実行した日を T（その日の日付）、基準日を D とする。未着手タスクの確定行は、
**現在の確定開始日**で次のように扱う。

| 未着手タスクの確定開始日 | 扱い |
|---|---|
| T より前（予定を過ぎたのに未着手＝遅れ） | 確定を消し、D 以降に置き直す |
| T 〜 D の前日 | **今の確定のまま残す**（予定どおり着手する前提） |
| D 以降 | 確定を消し、D 以降に置き直す |

- **D = T なら真ん中の区間は空**になり、元の「未着手はすべて置き直す」と同じ動きに
  なる。未来の基準日は、この規則の自然な拡張であって別の仕組みではない。
- これが無いと、D を未来にしたとき **T〜D の間に未着手の仕事が1件も入らない計画**に
  なる（今週着手予定だったタスクまで D 以降へ押し出される）。
- 残した確定行は他の確定行と同じくパス1で先に予約されるので、D 以降に置き直す
  タスクとのライン数の取り合いも既存の2パス構成で解決される。
- T を参照するのは**再計画という明示操作の瞬間だけ**で、結果は確定行として保存
  される。スケジューラ自体は引き続き `today()` を見ない（8-1 (a) の決定論性は崩れない）。
- ダイアログには「9/28 より前に開始予定の未着手タスク 14件は、今の確定のまま
  残します」のように件数を出す。

ダイアログでの基準日:

- **初期値は今日（T）**。未来にしたいときだけ変える。
- **過去の日付も指定できるが、警告を出してから実行する**（「今日より前に置かれる
  タスクが出ます」）。先週付けで組み直すような使い方を残すため、禁止はしない。
- 再計画を実行した日 T は `project` に保存する（仮に `replanned_at`）。状態帯の表示
  （8-7）と、下記「過去の違反をノイズにしない」の境界に使う。

#### 「確定を無視して計算」

ガントチャートタブにチェックボックスを1つ置き、オンの間は
`confirmed_schedule` を読まずに計算する（手動ピンは効かせる）。確定データには
触れないのでいつでも戻せる。

これが無いと、確定後は「このジョブを足したら本来どうなるのか」を試すために
確定を解除するしかなくなる。チェックボックス1つで、**確定によって失われる
シミュレーション性を、データモデルを一切変えずに取り戻せる**。

#### 過去の違反をノイズにしない

再計画を繰り返すと、基準日以前の固定同士の重なりが `Constraint_Violation` に
積み上がる（§4-1 で既に指摘されている点）。**再計画を実行した日（`replanned_at`）
より前の衝突は報告しない**ルールが実質必須になる。

境界を基準日 D ではなく実行日 T にするのは、D が未来のとき、T〜D に残した確定行
（まだ起きていない予定）の衝突まで黙らせてしまうため。「もう変えようがない過去」
は T より前だけである。D = T の通常の再計画では、どちらでも同じ結果になる。

### 8-7. 確定状態の見せ方

確定を入れると、**ジョブ作成タブとガントチャートタブで「今どの状態なのか」が
見えなくなる**のが最大の使い勝手上のリスクになる。迷いどころは4種類ある。

| # | ユーザーが迷うこと | 主な場所 |
|---|---|---|
| ① | このファイルは確定済みなのか（全体の状態） | 両タブ |
| ② | どのタスクが確定で、どれが未確定か（確定後に足したジョブ・タスクは未確定で混在する） | 両タブ |
| ③ | 確定後に入力を変えたのに日程が動かない | ジョブ作成タブ |
| ④ | 今見ているのは確定か試算か | ガントチャートタブ |

**③が最も危険。** 確定行は `days`・`team_id` を持つ（8-2）ため、確定後にタスク上書きの
日数やチームを変えても、再計画するまで確定済みタスクには反映されない。何も
エラーが出ずに「入力したのに何も起きない」状態になり、操作ミスと区別がつかない。

#### 状態帯（両タブの最上部に常時表示。①）

背景色で3状態を区別する。

| 状態 | 色 | 表示内容 | 置くもの（ガントチャートタブのみ） |
|---|---|---|---|
| 未確定 | 灰 | 「未確定 — 編集するたびに日程を計算し直します」 | 「確定する…」 |
| 確定済み | 緑 | 確定日 ｜ 未確定のタスク N件 ｜ **確定後の変更で未反映 N件**（赤文字。0件なら出さない） | 「確定を無視して計算」チェック、「再計画する…」「確定を解除」 |
| 試算中（確定を無視して計算がオン） | 橙 | 「試算を表示中 — 保存されている確定とは異なります」 ｜ 確定から動いたタスク N件（最大 +N営業日） | 「確定を無視して計算」チェック |

- 再計画した後は、確定日の代わりに「**9/28 から新計画（9/24 再計画）**」と基準日と
  実行日を出す。最初に確定しただけのときは基準日を出さない。
- **操作ボタンはガントチャートタブの帯にだけ置く**。結果を見ながら操作する場所に
  限定し、ジョブ作成タブの帯は表示だけにする。
- 確定した日時を出すため、`project` に確定日時（仮に `confirmed_at`）を持つ。

#### ジョブ作成タブ（②③）

- ジョブ一覧に「確定」列: 確定／一部未確定（件数）／未確定（斜線）。絞り込みにも
  「確定状態」を足し、確定後に足したジョブを探せるようにする。
- タスク上書きに「確定日程」列（表示専用）: 確定した開始〜終了・日数・チーム。
  確定行の無いタスクは斜線で「未確定」。
- **未反映の変更**: 入力値が確定値と違うセル（日数上書き・チーム上書き等）は
  **値を赤文字**にし、ツールチップで「確定値: 16日 → 入力: 20日。『再計画する』と
  日程に反映されます」と出す。**編集は禁止しない**——次の再計画に向けて入力を
  直しておく使い方は正当なので、ロックではなく表示で知らせる。

#### ガントチャートタブ（②④）

- **例外にだけ印を付ける。** 確定後はほぼ全部が確定済みになるので、確定済みは
  印なし（通常表示）。8-2 の「ピンは希少であることに価値がある」と同じ考え方。
  - 未確定のバー: 斜線の塗り。下端の細い帯でチーム色を残す
  - 手動ピン（`start_pin_date`）: バー左上に▼。確定とは無関係に今すぐ役に立つ
- 既存の強調枠（締切超過＝赤の太枠、固定どおりに置けない＝橙の破線）は、
  バーの塗りが枠と同系色（カットシーンの赤いバー等）だと埋もれるため、
  **枠の内側に白い枠を入れる**。これも確定とは独立に入れられる。
- 試算中は、**確定していた位置をバーの下に灰色の細線で重ねる**（MS Project の
  ベースライン表示と同じ）。バーと細線のずれが「確定から動く所」になる。確定行の
  無いタスクには細線が無い。ツールチップに確定日と試算日を並べる。確定機能と
  同時に作る（「確定を無視して計算」だけでは、何がどれだけ動くのかが分からない）。

### 8-8. 残っている論点

- **「完了しているのに、ユーザーが手で無効にしてある」タスク**が廃止されると、
  8-4 のルールでは有効に変わる。もともと矛盾した状態であり「実施した事実は残す」
  という原則としては正しいが、唯一手動設定が無視される箇所
- **ワークフローの全タスクを廃止できてしまう**と、そのワークフローを使うジョブが
  空になる。止めるか警告するか
- **マイルストーン単位の部分確定**（「このマイルストーンまで確定」）は、
  必要になってから実装する
- **確定と `.pschedule` の互換性**。確定行を持つファイルを旧バージョンで開くと
  確定が無視されるため、`check_openable()` のバージョン検証で弾かれることを確認しておく

### 8-9. 着手順

1. `jobs` に安定キーを足して jitter のID依存を切る（8-1）／
   `project.replan_base_date` を足す（8-3）
2. `confirmed_schedule` と「確定する／確定を解除する」（8-2、8-6）＋
   確定状態の見せ方（状態帯、ジョブ作成タブの「確定」「確定日程」列と未反映の
   赤文字、ガントの未確定の斜線）（8-7）
3. 「確定を無視して計算」＋試算中の状態帯と確定位置の細線（8-6、8-7）
4. 「再計画する」（未来・過去の基準日の扱いを含む）＋実行日以前の違反抑制（8-6）
5. `workflow_tasks.is_retired` と廃止（8-4）
6. 不変条件の検査（8-4）

1〜4 だけで合意形成サイクルは回る。5〜6 は「合意後にワークフローを直したとき」の
安全装置なので、実際にその運用が始まってからでも間に合う。

8-7 のうち、ガントの**手動ピンの▼**と**強調枠の白い内枠**は確定に依存しないので、
確定より先に単独で入れてもよい。
